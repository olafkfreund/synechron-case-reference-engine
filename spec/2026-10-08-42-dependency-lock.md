# Spec: Reproducible image builds from a CPU-torch lock

## Design

**uv makes the lock, pip installs it** (intent question 1).

- **`requirements.lock`** at the repo root, generated by `uv pip compile`:
  every package, transitive ones included, with an exact version and
  `--generate-hashes`. It is generated for Python 3.12 on
  `x86_64-manylinux_2_28` (the ECS default, `cpu_architecture = X86_64`),
  and includes the `dev` extra.
- **CPU torch:** `--torch-backend cpu` makes uv take torch and torchvision
  from the PyTorch CPU index (`torch==2.14.1+cpu`), and everything else from
  PyPI only. This is the reason for uv: pip-tools would need
  `--extra-index-url` for the whole resolve and could pick CUDA torch from
  PyPI, which is what the stray `uv.lock` did.
- **uv is not installed anywhere.** The lock command runs in the pinned image
  `ghcr.io/astral-sh/uv:0.12.23-python3.12-trixie-slim`, and the README gives
  the one command:

  ```sh
  docker run --rm -v "$PWD:/w" -w /w ghcr.io/astral-sh/uv:0.12.23-python3.12-trixie-slim \
    uv pip compile pyproject.toml --extra dev --torch-backend cpu --python-version 3.12 \
    --python-platform x86_64-manylinux_2_28 --generate-hashes -o requirements.lock
  ```

  - Re-running it keeps the existing pins and only resolves what changed in
    `pyproject.toml`. Add `--upgrade-package X` (one package) or `--upgrade`
    (everything) to move versions. The change shows in the PR diff, and CI
    builds it (intent question 3: by hand, no Dependabot).
  - The first lock is made with today's working image's `pip freeze` as
    constraints. It contains exactly the 147 packages that image has
    (checked: the diff against the freeze is empty), so app behaviour
    doesn't change.

**Dockerfile:**

```dockerfile
COPY pyproject.toml requirements.lock ./
RUN pip install --require-hashes --no-deps -r requirements.lock --extra-index-url https://download.pytorch.org/whl/cpu
RUN mkdir app && touch app/__init__.py && pip install --no-deps -e . && pip check
```

- This replaces the separate torch layer and `pip install -e ".[dev]"`.
- `--require-hashes` means a package that differs from the lock fails the
  build, whichever index served it. That also makes the CPU extra index safe.
- `--no-deps` stops pip from resolving anything itself.
- `pip check` fails the build if `pyproject.toml` names a dependency that
  isn't in the lock (someone forgot to re-lock). This catches drift without
  a new CI step.
- The model download, the RDS CA bundle and the apt packages are unchanged.

**`pyproject.toml`:** the names stay unversioned; the lock holds the
versions. The `rapidocr<3.10` cap from #70 comes out, because the lock pins
3.9.2. A later `--upgrade` that picks rapidocr 3.10 breaks the build in that
PR's CI, not on main, which is the point of the lock.

**Out of scope** (intent questions 2 and 4): there is still one image with
the dev extra, and the apt packages stay unpinned.

## Alternatives rejected

- **pip-tools (`pip-compile`).** It needs a new tool, and it handles the
  torch index only through `--extra-index-url` for every package. That brings
  back the CUDA-torch risk and a dependency-confusion surface.
- **`uv lock` (`uv.lock`) and `uv sync` in the image.** That adds uv to the
  image and changes the install path. `uv pip compile` gives a standard
  requirements file that plain pip installs.
- **`pip freeze` of a built image as the lock.** No hashes, and updating it
  means building unpinned first.
- **Pin versions in `pyproject.toml`.** That pins direct dependencies only.
  Today's break came from a transitive one (rapidocr, via docling).
- **A universal lock** (`--universal`, x86_64 and ARM64). Nobody runs ARM64,
  and torch's CPU wheels differ by platform. See Risks.

## Risks

- **ARM64:** the lock is for x86_64. Switching `cpu_architecture` to ARM64
  needs a re-lock with `--python-platform aarch64-manylinux_2_28` (or
  `--universal`). I'll note this in the README and next to the variable in
  `infra/variables.tf`.
- **The PyTorch CPU index removes old wheels:** a rebuild then fails loudly
  (hash or not found), and never installs something else. Fix: re-lock torch.
- **Build cache:** torch no longer has its own layer, so any lock change
  re-downloads everything. That costs a few minutes of CI time per
  dependency PR.
- **Hosts:** the app, worker and web images on ECS. The same versions as
  today, so no runtime change. Rollback is a revert.

## Verification

- A probe build (already done) installs the lock with `--require-hashes`.
  It gets `torch 2.14.1+cpu`, no `nvidia-*` packages, `pip check` passes,
  and site-packages is 2.1 GB, the same as today.
- `docker compose build --no-cache app && docker compose run --rm app
  pytest` is green.
- Two `--no-cache` builds give an identical `pip freeze`.
- Drift check: adding an unlocked dependency to `pyproject.toml` fails the
  build at `pip check`. Try it, then revert.
- Re-running the lock command with no changes leaves `requirements.lock`
  unchanged (apart from the header).
