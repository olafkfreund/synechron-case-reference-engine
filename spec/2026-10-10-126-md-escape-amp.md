# Spec: Markdown output does not escape &, so an HTML entity can spell a protected name

## Design

`&` is added to the escape class in `render.md()` (`app/render.py:276`), and
to the docstring's list:

```python
    s = re.sub(r"([\\`*_\[\]<>#|~&])", r"\\\1", " ".join(str(s).split()))
```

- **Why it works.** CommonMark treats `\&` as a backslash escape of ASCII
  punctuation: the text renders as `&`, and no entity is decoded. So
  `Zo&#114;p` renders literally, and "R&D" still reads "R&D".
- **Every value is covered.** Each value in the `MD` template goes through
  `| md` (`:282-330`). That includes the industry quote, publisher and URL.
  The only exceptions are the static headings and labels the code writes
  itself.

## Alternatives rejected

- **Replace `&` with `&amp;`.** That also works, but raw `&amp;` would appear
  in plain-text Markdown readers. A backslash escape is the module's existing
  idiom.
- **Decode entities before `blocked()`.** That checks the decoded text but
  still ships the entity, and it duplicates HTML decoding in the anonymiser.
  Escaping makes the Markdown display exactly the text that was checked.

## Risks

- **URLs show a backslash before `&`** in viewers that do not apply
  CommonMark escapes, the same way they already do for `_` in URLs. Plain-text
  readers see `\&`, which is the existing trade-off for every escaped
  character.
- **DOCX, PPTX and PDF are untouched.**
- **No host impact.**

## Verification

New tests in `tests/test_render.py`:

- `render.md("Zo&#114;p")` contains `\&#114;`, and never a bare `&#`. This
  fails on main.
- `render.md("R&D")` is `R\&D`.
- The existing `test_markdown_fields_and_escaping` and
  `test_markdown_values_cannot_create_structure` still pass. Any assert that
  depended on an unescaped `&` is updated and named in the plan.

The full suite passes.
