# Spec: The local model's JSON replies are data, not the schema

## Design

Everything lives in `app/llm.py` `complete_json()` (`:76-122`), so all 8
callers benefit, and none of them changes unless the eval in step 4 says so.

### 1. Detect a schema echo

Add `_schema_echo(text: str, schema: dict) -> bool`. It returns true when the
reply parses as a JSON object and either:

- **top-level echo:** the object has at least 2 of the keys `$defs`,
  `properties`, `required`, `additionalProperties`, `type`, `title`, and none
  of the model's own required field names; or
- **one level down:** a single top-level key holds an object that matches
  the first test, as in `{"Claims": {"properties": …}}`.

It is pure, with no I/O, and is never fooled by a real reply. Our models
have no field named `properties` or `$defs`, and a test checks that for
every `complete_json` model.

### 2. One corrective retry

- **When it retries.** A reply that fails validation *and* is a schema echo
  is retried once.
- **The retried messages** are the same system and user messages, plus:
  - the model's own reply as an `assistant` turn
  - a short `user` turn: "That was the schema, not the answer. Reply with
    one JSON object containing the data, using the field names above. Do not
    include the schema."
- **Why the corrective turn is needed.** `temperature=0` would otherwise
  return the same echo.
- **Any other validation failure** is not retried. It is a different
  problem, and a retry doubles the cost.
- **A second failure** raises the existing
  `ValueError("… reply is not a valid …")` with the extra text
  "(after a schema-echo retry)", so callers handle it exactly as today.
- **Limits.** The retry uses the same `extra` options, timeout,
  `MAX_TOKENS` and truncation check. The overflow guard counts the longer
  prompt: when `est` with the retry turn would exceed `num_ctx`, there is no
  retry and the call raises.

### 3. A less echo-prone prompt cue (JSON mode only)

Today the cue reads `Reply with JSON matching this schema: {…}`. Replace it
with:

```text
Reply with one JSON object that follows this JSON Schema. The schema describes the format; do not repeat it.
Schema: {…}
Example of the shape (values are placeholders): {…}
```

- **The example** is built by code from the schema (`_example(schema)`):
  - strings `"…"`
  - numbers `0`
  - arrays with one example item
  - enums take the first value
  - `$ref`s resolved

  It is deterministic and has no content.
- **Size check.** The example adds a few hundred characters. The
  `num_ctx` overflow guard and the research `page_chars()` budget both
  count system prompt length, so they adapt. A test checks that the
  `page_chars` budget still exceeds 500 at the README `num_ctx`.

### 4. Logging and eval

- **Logging.** On every retry,
  `log.warning("schema echo: alias=%s model=%s schema=%s", alias,
  model_cls.__name__, …)`, with no content. It is recorded in an
  in-process counter `llm.ECHO_RETRIES` for tests.
- **`scripts/eval_json.py` (new):**
  - Arguments: `--calls claims,brief`, `--n 20`, and `--mode json|schema`.
  - It reads one stored research row with the most pages, the "demand
    forecasting" query (id given on the command line), and a stored brief
    input from the demo DB.
  - It runs the call N times, with a cache-busting nonce comment in the
    user message so Ollama doesn't reuse a KV prefix.
  - It prints counts only: success, schema echo, other validation failure,
    retries, and mean seconds.
- **Before and after, on local `qwen3:14b`:**
  - main (`json` mode, no retry)
  - this branch (`json` mode, new cue and retry)
  - `schema` mode on the same two calls, for comparison
- **Decision rule, recorded in the plan.** A call gets a per-call
  `mode="schema"` override only if `schema` mode, over 20 runs, has 0
  echoes, at least as many successes as the new `json` mode, and no fall in
  claims per reply. Otherwise everything stays in `json` mode with the
  retry.

## Alternatives rejected

- **Enforced `format` for all local calls.** The #53 eval showed collapse
  ("title only") on extraction. Enforced mode is only considered per call,
  by measurement.
- **Retry on any validation error.** That doubles the cost on real shape
  errors, and the second try rarely fixes them at `temperature=0`.
- **Raising the temperature on retry.** It makes replies vary and makes
  verbatim quotes less likely.
- **Post-processing the echo into data.** There is no data in an echo to
  recover.

## Risks

- **A false positive** retries a valid reply. A valid reply never fails
  validation, so detection runs only after a failure, which removes that
  risk.
- **Extra latency:** one more call (about 20 s locally) on an echo. That is
  acceptable against a failed research run.
- **The new cue could change extraction quality.** `eval_extraction.py` is
  re-run on the 11 trial documents, counts only, and the plan's gate is "no
  drop in sourced items per document beyond run-to-run noise".

## Verification

- **Unit tests** (`tests/test_llm.py`, with litellm stubbed):
  - Echo, then a valid reply: it returns the data, with one retry and the
    corrective turn present.
  - Echo twice: it raises "after a schema-echo retry".
  - A nested echo is detected.
  - A non-echo validation error gives no retry.
  - The retry is skipped when it would overflow `num_ctx`.
  - The log line holds no content.
  - No `complete_json` model has a field named like a schema keyword.
  - `_example()` is deterministic and validates the shape keys.
- **Evals:** `scripts/eval_json.py` before and after, as in step 4, and
  `scripts/eval_extraction.py` on the trial documents. Counts only.
- **By hand:** in the demo, re-run the "demand forecasting" research. Claims
  are extracted, or the log shows a retry.
- **Full suite:**
  `docker compose build app && docker compose run --rm app pytest`.
