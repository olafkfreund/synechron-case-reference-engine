# Spec: Portal UI matches the approved mockup

## Design

The approved intent answers: IBM Plex is served by the app; there is one
static stylesheet; pages the mockup doesn't show use the same components.
The reference is the mockup's `project/Main.dc.html` (README "Links"); its
colours and sizes are copied exactly.

**Static files.**
- `app/main.py` mounts `app/static/` at `/static` with FastAPI's built-in
  `StaticFiles` (Starlette, already installed; no new dependency).
- It's public, like `/healthz`: CSS and fonts hold no data, and the login
  page needs them before a session exists.
- `app/static/portal.css` holds all styles. `app/static/fonts/` holds IBM
  Plex Sans 400, 500 and 600 and IBM Plex Mono 400, as `.woff2` from the
  official IBM release (OFL 1.1), with `OFL.txt` beside them. `@font-face`
  uses `font-display: swap`, and the stack falls back to `system-ui`.

**Tokens, at the top of `portal.css` as CSS variables:**

| Token | Value | Used for |
|---|---|---|
| `--ink` | `#1B2430` | text, header, dark buttons |
| `--ground` | `#F6F5F1` | page |
| `--card` | `#FFFFFF`, border `#DAD7CF`, radius 10px | cards, table boxes |
| `--accent` | `#0B6A6A` (hover `#084F4F`) | primary buttons, links, focus ring |
| `--muted` | `#55606E` | secondary text |
| `--line` | `#ECE9E2` | row lines |
| `--head` | `#F1EFEA` | table header tint |
| ok / warn / bad / neutral | `#E5F2E9`/`#1E6B3A`, `#FBF0D9`/`#6B4600`, `#F3E3E1`/`#8A2A1E`, `#EEF1F4`/`#3D4652` | badges and notes |

All text pairs are at least 4.5:1, as in the mockup.

**Components (classes, no inline styles):**
- `.card`, `.badge` plus `.ok`, `.warn` and `.bad`;
- `.btn` (secondary outline), `.btn.primary` (teal) and `.btn.dark`
  (downloads), all at least 44px tall;
- `.note` (amber), `.tag` (mono tech tag), `.mono` (metadata);
- `.table-box` (a scrolling box around wide tables), `.stack` (a vertical
  gap), `.row` (a wrapping flex row).

The existing `.bad`, `.ok`, `.empty`, `.badge` and `.note` names are kept,
so the templates and tests that use them still work.

**`base.html`:**
- A navy header: "Reference Engine", then "bids & presales" in mono, then
  the navigation, then the user's initials, name and role, and Log out.
- The navigation is plain links, the mockup's tabs:
  - everyone: Find references (`/search`) and Research (`/research`);
  - reviewers: Review queue;
  - admins: Sources, Client registry, Model approvals, Audit.

  The current page's link has `aria-current="page"` and the white "pressed"
  style; the template gets the path from `request.url.path`.
- `<main>` is 1200px max with the mockup's padding, a skip link, and a
  `<link>` to `/static/portal.css`. The mockup's "illustrative sample data"
  banner is not copied.

**Pages (markup and classes only; the same routes, form field names and
values, and buttons):**
- `landing.html`: a heading, then one card per page the user may use, with
  the page's one-line purpose, so each card is a link.
- `search.html`, following the mockup's "Find references":
  - the bid box is a card with a label, the filters and a primary button;
  - each result is a card: the mono meta line, the title, the client label
    with an "Anonymised" or "Named" badge, the basis badge, "Why it fits",
    outcomes, tech tags, the tailored-wording box ("to copy, not included
    in downloads"), and a row with Research (outline) and the five
    download buttons (dark).

  The mockup's "Show source" and "Copy wording" need JavaScript, so they're
  left out.
- `review_list.html` and `review_detail.html`, following the mockup's review
  queue: card, table, badges for sourced, unsourced and empty, amber notes,
  and Approve as the primary button.
  - The editable inputs stay, styled.
  - The add and remove rows (#40), the add-to-registry form (#41) and the
    merge parts (#55) get the same classes.
- `sources.html`, `clients.html`, `audit.html` and `models.html`: the
  intro line in `--muted`, the table in a `.table-box`, and the forms as
  cards.
- `research*.html`: the mockup's numbered steps as cards, and the claims
  table in a `.table-box`.

**Merge order:** #55 (PR open) also edits the review templates, so #55
merges first and this branch rebases onto it.

## Alternatives rejected

- **Google Fonts:** each page view tells Google which page a user opened,
  and fails behind proxies (intent question 1).
- **A CSS framework (Tailwind, Bootstrap):** a build step or a large file
  for a small app; the mockup's styles are a few hundred lines of CSS.
- **Inline styles copied from the mockup:** hard to keep consistent across
  12 templates. Classes keep markup short and the look in one file.
- **Keeping the CSS in `base.html`:** it's re-sent with every page; a
  static file is cached.

## Risks

- **Tests that match exact markup** (for example `"<tr>\n<form" not in
  page`, `'value="remove"'`, button text, `class="badge bad"`): form
  names, values and button text are kept; only wrappers and classes are
  added. Any test that still breaks is updated, and the plan lists it.
- **The `/static` route must not leak anything:** only `app/static/` is
  served, with no directory listing (StaticFiles has none), and no user
  data is ever written there.
- **The font licence:** OFL allows bundling; the licence file ships with
  the fonts.
- **Long tables on a phone:** `.table-box` scrolls horizontally. Header
  links wrap.

## Verification

- `docker compose build app && docker compose run --rm app pytest`: green.
- A new `tests/test_ui.py`:
  - `/static/portal.css` and one font return 200 without a session;
  - every page, for its role, links `portal.css`, has no `<script` and has
    the navigation;
  - `aria-current="page"` is on the current tab;
  - `nobody` sees no admin tabs.
- Manual: each page as each role in the local portal, at desktop and phone
  width, checked against the mockup. Screenshots go in the PR.
