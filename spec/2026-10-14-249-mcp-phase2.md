# Spec: MCP server, phase 2 (outputs, research, library, briefs)

Phase 1 (#256) shipped identity, the token-to-`User` gate, the approved-client
allowlist, the `tool_calls` audit and four read-only tools. Phase 2 adds the
tools that **create things**: document downloads, public research, the
library and briefs. It follows the approved design (`docs/mcp-design.md`
sections 4 and 6) and keeps every phase 1 rule:
- plain-user view
- `/go` links only
- portal functions only
- audit without content
- per-user rate limit

## Design

### 1. Lift the route bodies into service functions, so both entry points share the rules

| New function | Lifted from | Notes |
|---|---|---|
| `render.produce(conn, user, fmt, case_ids, research_id, ack, library_ids) -> (bytes, mime, filename)` | `render.generate` body (`app/render.py:811-833`) | `build()`, then images, `make`, and the `generations` insert. `generate` becomes a thin wrapper and the bytes are unchanged. |
| `research.start(conn, user, question, case_id=None) -> rid` | `POST /research/send` (`app/research.py:156-168`) | the query scrubbing, insert and job exactly as today |
| `library.save_item(conn, user, research_id, brief_id, n, topic) -> lid` | `POST /library/save` body (`app/library.py:69-115`) | |
| `brief.create(conn, user, rid, n, title) -> bid` | `brief.start` (`app/brief.py:134-148`) | |
| `brief.output(conn, user, bid, fmt) -> (bytes, mime, filename)` | `brief.download` (`app/brief.py:194-…`) | |
| `library.output(conn, user, lid, fmt)` | `library.download` (`app/library.py:243-…`) | |

The portal routes call these functions and behave exactly as before. That is
tested by the existing route tests staying green, plus byte-equality tests.

### 2. Downloads: a signed link, never a file in the tool result

- **What `generate_output` returns.** It validates by calling `render.build`
  (no bytes, no audit row), then returns:
  - `download_url` = `{APP_ORIGIN}/mcp/download/{token}`
  - `expires_in` = 600
  - the Markdown preview text, the same as `preview_output`
- **The token.** An `itsdangerous` `URLSafeTimedSerializer`, salted
  `"mcp-download"`, keyed by the app secret, over `{k: user_key, f: fmt,
  c: case_ids, r: research_id, a: ack, l: library_ids, kind: "case"}`, with a
  10-minute max age.
  - Briefs and library items use the same token with `kind:"brief"` or
    `"library"` and an `id`.
  - Nothing is stored server-side.
- **`GET /mcp/download/{token}`.** It authenticates with **either** the
  portal session **or** a bearer token, through the phase 1 gate's
  `user_from_token`. In both cases the token's user key must equal the
  caller's key: someone else's link gives 403.
  - It re-runs `render.produce()` (or `brief.output`/`library.output`) with
    the caller's current rights, so a case hidden since the link was made
    gives 404.
  - The `generations` row is written here, when bytes actually leave.
  - Headers: `Content-Disposition: attachment`, `Cache-Control: no-store`,
    `X-Content-Type-Options: nosniff`.
  - An expired or tampered token gives 410, "this download link has
    expired; ask for a new one". A tampered token is reported as expired,
    so nothing about it is revealed.
  - The token value is never logged and never written to `tool_calls`.
- **Route registration.** The route is registered in the main FastAPI app
  (not the MCP sub-app), so the cookie path works. Its CSRF exemption is
  moot, because it is a GET.

### 3. Research, library and brief tools

All tools use the phase 1 wrapper (user from the token, plain-user view,
audit row, rate limit, untrusted-content preface, portal error messages).

| Tool | Hints | Calls | Returns |
|---|---|---|---|
| `start_research(question≤1000, case_id?)` | open-world, not idempotent | `research.build_query` (the client-name scrub) then `research.start` | `research_id`, the **scrubbed query that will be sent** (shown, as the portal preview does) and `status: queued` |
| `get_research(research_id)` | read-only | the same visibility as `/research/{rid}`: owner only | status, the scrubbed query, and claims through `visible_claims` (protected names dropped), each with type, statement, quote, publisher, `/go`-free URL and date. Technical notes stay verbatim. |
| `save_library_item(research_id? \| brief_id?, n[], topic?)` | not idempotent | `library.save_item` | `library_id` |
| `list_library(q?, topic?, kind?)` | read-only | the same rows as `/library` | id, topic, kind, sources count, age, stale, saved by |
| `get_library_item(library_id)` | read-only | `library.view` logic | quotes or brief, through the same `apply()`/`blocked()` as the portal |
| `create_brief(research_id, n[], title?)` | not idempotent | `brief.create` | `brief_id`, `status: queued` |
| `get_brief(brief_id)` | read-only | owner only | the brief body, through `brief_section` (`Withheld` gives an `isError` with the portal's text) |
| `download_brief(brief_id, format)`, `download_library_item(library_id, format)` | read-only (the link writes the audit) | | a signed link, as in section 2 |

- **External URLs in research.** URLs of **public** web sources are
  returned, because they are public pages the portal also links. That is
  different from internal document URLs, which stay behind `/go`.
- **Deferred:** `delete_library_item` and re-check are not exposed in
  phase 2.

### 4. Approved-client and data rules

- **Classification:** research and briefs are `public` data. Case outputs
  are the sanitised product. Both may go to the client LLM under the design
  (the third-party destination rule).
- **Untrusted content:** research claims are web text. The phase 1
  untrusted preface applies, and technical notes are capped at the
  portal's limit.
- **Rate limits:** the phase 1 60/min per user applies. In addition,
  `start_research` and `create_brief` are limited to 10 a day per user,
  counted in `tool_calls`, because each one starts a Brave search and model
  jobs.

## Alternatives rejected

- **Base64 files in the tool result.** They fill the model's context and
  can't be opened by most clients. The signed link is what the design
  approved.
- **Pre-signed S3 URLs.** These files are generated, not stored, and an S3
  URL would skip the per-user check and the `generations` audit.
- **A stored download-token table.** A signed, timed token needs no
  storage and no cleanup, and re-running `produce()` on download keeps
  rights current.

## Risks

- **Link sharing.** A link is bound to the user key and needs that user's
  session or token, so a forwarded link gives 403.
- **Generation cost.** The file is built on download, as `/generate` does,
  and is limited by the per-user rate limit and the existing PDF timeout.
- **Brave usage.** Research costs real searches. The daily cap bounds it.
- **Refactor regressions.** The lifts are behaviour-preserving, and the
  portal route tests plus new byte-equality tests catch drift.

## Verification

- **Lifts.** Every existing render, research, library and brief route test
  stays green. Byte-equality: `/generate` output before and after the lift,
  for each format, on the same input.
- **Downloads.**
  - A link works with a session or a bearer token for the same user.
  - Another user gets 403.
  - Expired or tampered gives 410.
  - A case hidden after the link was made gives 404.
  - The `generations` row is written on download, not on `generate_output`.
  - `no-store` is set.
  - The token is absent from logs and `tool_calls`.
- **Tools.** Each `structuredContent` matches its `outputSchema`.
  - `start_research` returns the same scrubbed query as the portal preview
    and queues one job.
  - `get_research` on someone else's research gives `not_found`.
  - Claims naming a protected client are dropped.
  - `save_library_item` and `create_brief` produce the same rows as the
    portal routes.
  - `get_brief` on a withheld brief gives the portal's message.
  - The daily caps apply.
- **Leaks.** No stored internal URL, `documents.text`, protected name, bid
  text or token appears in any output, error, log or `tool_calls` row.
- **Smoke test.** In a local stack with `MCP_ENABLED=1`:
  1. `start_research`, wait, then `get_research`
  2. `create_brief`, then `get_brief`
  3. `generate_output` and fetch the link with the bearer token, giving a
     200 docx
- **Reviews:** Opus and Codex, read-only.
- **Full suite:**
  `docker compose build app && docker compose run --rm app pytest`.
