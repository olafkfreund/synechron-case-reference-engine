# Spec: Client logos in the registry and in outputs

The intent's questions were approved as proposed (2026-10-14):

1. **Placement:**
   - case-study cover: top-right, 40 mm wide at most
   - bid pack: beside the case title, 25 mm at most
   - slide: top-right corner
2. **Search cards** show a 24 px logo, in place of the building icon, for
   referenceable clients whose logo is allowed.

## Design

### 1. Storage and decoding: the case-diagram pattern

- **Table.** `client_logos(id bigserial pk, client_id bigint not null
  unique references clients(id) on delete cascade, raw bytea, png bytea,
  width int, height int, reason text, created_by text not null,
  created_at timestamptz default now())`.
  - There is one row per client, replaced on a new upload.
  - It is a separate table, so `clients` and its `VERSION` hash are
    unchanged.
- **Upload.** `POST /admin/clients/{cid}/logo` (admin, multipart):
  - **Accepted:** PNG or JPEG, checked by magic bytes; 1 MiB at most
    (`LOGO_MAX_BYTES`), with the guard's body cap set for this path.
  - **Stored:** `raw`, with `png` cleared.
  - **Queued:** a `logo` job.
  - **Decoded by the worker, never the web process.** It reuses
    `diagrams._decode()`, which does the bomb check before decoding,
    re-encodes to PNG and strips metadata. It writes `png`, `width` and
    `height`, or a `reason` on rejection. `raw` is cleared after decoding.
  - **Shape check.** A logo under 64 px on its short side, or with an
    aspect ratio beyond 8:1, is rejected with a reason.
- **Remove.** `POST /admin/clients/{cid}/logo/remove` deletes the row.
- **Serve.** `GET /admin/clients/{cid}/logo.png` (admin) for the registry
  preview, with `PNG_HEADERS`. `GET /logos/{cid}.png` (any user) serves
  **only when the client is referenceable and logo-allowed**, and gives
  404 otherwise.

### 2. The display rule, in one place

`logo_for(conn, client_id) -> bytes | None` returns the PNG only when **all**
of these hold:
- `clients.referenceable` is true
- `clients.logo_allowed` is true
- a decoded `png` exists

Every output and page asks this one function. Turning either flag off
removes the logo from the next render.

A protected (non-referenceable) client never gets a logo anywhere: no
output, no search card, no public route.

### 3. Where it appears

| Place | How |
|---|---|
| Bid pack docx (`render.to_docx`) | an `InlineImage` beside the case title, 25 mm wide at most (template field `c.logo`) |
| Case-study docx and pdf | top-right of the cover, 40 mm wide at most (template field `c.logo`) |
| Slides (`to_pptx`) | top-right corner picture, 25 mm high at most |
| Markdown | no image; nothing is added |
| Preview and search cards | `<img src="/logos/{cid}.png" alt="{name} logo">` at 24 px, in place of the building icon |

- **Templates.** The fields come from
  `scripts/make_reference_template.py`, regenerated, never hand-edited.
  The fields are conditional, so a client with no logo leaves no gap.

### 4. Registry UI (`clients.html`)

Each client's Edit panel gets a "Logo" field with:
- the current preview, from the admin route
- its status: none, processing, ready, or rejected with the reason
- an upload input
- Remove

The badge row shows "Logo ready" next to "Logo allowed". Existing
classes and tokens only.

### 5. Audit

Each upload and removal writes a row in the existing registry audit, or a
new append-only `client_logo_changes(client_id, action, by, at)` following
`architecture_changes`. It is listed in `/admin/audit`.

## Alternatives rejected

- **SVG logos.** They are scriptable and need a sanitiser. Raster only.
- **Decoding in the web process.** The diagram work deliberately moved
  parsing to the worker. A logo follows the same rule.
- **Logos for protected clients behind a reviewer tick.** A logo
  identifies the client, so protected means none.

## Risks

- **Template regeneration.** It touches `brand/*.docx`. #213 and #231(c)
  also edit `make_reference_template.py`, so whichever merges last
  regenerates all templates from the merged script.
- **Low-quality logos in customer documents.** Mitigated by the minimum
  size and aspect checks, plus the registry preview.

## Verification

- **Tests:**
  - **Upload:** the type and size refusals, and admin-only access.
  - **Worker decode:** a PNG and a JPEG succeed; a bomb, a tiny image, an
    extreme aspect ratio and garbage are rejected.
  - **`logo_for`:** a truth table over referenceable × allowed × decoded.
  - **The public route:** 404 unless both flags are set.
  - **Outputs:**
    - the docx, case study and pptx contain the image only for an allowed
      client, with no image otherwise and no gap
    - a protected client never gets a logo, in any format
  - **Audit:** rows for upload and removal.
- **Full suite:**
  `docker compose build app && docker compose run --rm app pytest`.
- **Screenshots:** the registry Edit panel with a logo, and a search card,
  in light and dark.
- **Reviews:** Opus, Codex and agy, read-only.
