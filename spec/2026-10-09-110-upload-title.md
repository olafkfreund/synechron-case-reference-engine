# Spec: Uploaded documents are titled with the stored key, not the file name

## Design

Approved answer A: change the key layout and leave the crawler alone. This is
one line of app code.

- `app/main.py:244`: the key changes from
  `f"{prefix}{uuid.uuid4().hex}-{name}"` to
  `f"{prefix}{uuid.uuid4().hex}/{name}"`.
- `app/crawl.py:62` already titles each document with
  `key.rsplit("/", 1)[-1]`. With the new key, that is `name`, the
  `safe_name()` result. No crawler change.

Why this holds:

- **No path parts in the name.** `safe_name()` (`app/main.py:75-79`) maps
  everything outside `[A-Za-z0-9._-]` to `_`, so `name` can't contain `/`.
  The title is always exactly `name`, extension included. That's the
  extension upload validated, which `to_markdown` needs.
- **Unique keys.** The uuid segment keeps two uploads of the same name
  apart, as before.
- **Prefixed listing still matches.** `crawl_s3` lists by prefix
  recursively, with no `Delimiter` in `app/crawl.py`, so objects one level
  deeper under the source prefix are still found.
- **No folder markers.** Upload never writes a key ending in `/`, so the
  crawler's folder-marker skip (`app/crawl.py:46`) doesn't drop these
  objects.
- **Unchanged identity.** `external_id` is still the full key, so document
  identity (`unique (source_id, external_id)`) and deletion detection don't
  change.

Approved answer 2: no backfill. Documents already uploaded keep their old
titles, and `scripts/demo.sh reset` clears the one demo document.

Tests:

- **`tests/test_auth.py:119`:** the key-shape assertion becomes
  `k.endswith("/My_Case_.DOCX")`. It also checks that the segment between
  the prefix and the name is 32 hex characters:
  `re.fullmatch(r"uploads/[0-9a-f]{32}/My_Case_\.DOCX", k)`. The old
  `".." not in k` and `"etc" not in k` checks stay.
- **New test in `tests/test_ingest.py`:** upload through `/admin/upload` into
  a moto bucket, then run `crawl.crawl_s3(sid)`, using the
  `test_crawl_cursor_and_deletion` setup as the pattern. It checks:
  - `documents.title` is the uploaded name, not the key;
  - `external_id` is the full key;
  - uploading the same name twice gives two documents with the same title
    and different `external_id`.

  A stubbed `to_markdown` or a tiny made-up PDF keeps the test fast, as the
  existing crawl tests do.

## Alternatives rejected

- **B, the original name in S3 metadata:** gives exact names with spaces
  and punctuation, but adds encoding and decoding, and a crawler branch with
  a fallback. Not approved.
- **C, strip a `<32 hex>-` prefix in the crawler:** would also rename a
  hand-filled file whose name happens to start that way.
- **Backfill the old titles:** production isn't deployed, and there's one
  demo document.

## Risks

- **Old and new layouts side by side.** Old uploads (`uuid-name`) and new
  ones (`uuid/name`) can sit in the same bucket, and both are still crawled.
  Only the titles differ. No host is affected beyond the upload bucket.
- **S3 console browsing.** It shows one "folder" per upload. That's
  cosmetic, and only admins use the console.
- **IAM and lifecycle rules.** Checked in `infra/`:
  - The web task's only S3 write grant is `s3:PutObject` on
    `${originals}/${var.upload_prefix}*` (`infra/iam.tf:91-94`). In IAM
    resource ARNs `*` also matches `/`, so `uploads/<uuid>/<name>` is still
    allowed.
  - The only S3 lifecycle rule is on the ALB log bucket (`infra/alb_logs.tf:33`),
    not on the originals.

## Verification

2. Manual check in the `refsdemo` stack after merge:
