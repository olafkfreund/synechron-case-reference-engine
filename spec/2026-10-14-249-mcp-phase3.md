# Spec: MCP server, phase 3 (uploads for everyone)

Phases 1 and 2 (#256, #258) let any signed-in user search, read, generate,
research and use the library over MCP. Phase 3 adds the decision recorded
in the design (`docs/mcp-design.md` section 5): **every signed-in user can
upload a document**. Uploads go into review and become visible to staff only
when a reviewer approves the case. Uploading works the same way from the
portal and from an AI agent.

## Design

### 1. One staff upload source, chosen by the admin

- **Which source.** The staff upload source is an existing `upload`-kind
  source whose config has `"staff": true`. The admin sets it on
  `/admin/sources`. If several have it, the lowest id wins.
  - Its `acl_groups` (for example the all-staff group) decide who sees
    approved cases. There is no new env var: the ACL lives where every other
    source keeps it.
  - If no source has `"staff": true`, uploads are off. The portal hides the
    page and the tool returns "uploads are not configured".
- **No change to `/admin/upload`.** Admins keep uploading to any upload
  source, with no quota.

### 2. `accept_upload`: the single entry point for portal and MCP

`ingest.accept_upload(conn, user, name, data) -> upload_id`:

1. Checks the file (lifted from `/admin/upload`, `app/main.py:295-304`, into
   `check_file(name, data)`, which the admin route also calls):
   - `safe_name`
   - the extension in `UPLOAD_MAGIC`
   - the size within `upload_cap()`
   - the magic bytes match
2. Applies the quota **atomically**, under
   `pg_advisory_xact_lock(hashtext('upload:'||user.sub))`: at most 20 uploads
   and 200 MiB per user over a rolling 24 h, counted in `uploads`.
   - Over the quota gives 429: "daily upload limit reached (20 files or
     200 MiB)".
3. `put_object` to `{prefix}{uuid}/{name}`, as the admin route does.
4. Inserts the `uploads` row and queues an **`ingest_upload` job** for that
   one key.
   - Today an upload queues a crawl of the whole source
     (`app/main.py:318`). A crawl already running returns `running`
     (`app/crawl.py:39`), so a file uploaded during a crawl waits for the
     daily schedule.
   - The new job reads the one object and calls `ingest(source_id, key,
     name, body)`. That is the same call the crawl makes, and `ingest`
     already tolerates an upload racing a crawl (`app/ingest.py:124`).

New table:

```sql
uploads(id bigserial pk, user_key text not null, user_name text not null,
        source_id bigint references sources, s3_key text not null,
        bytes int not null, job_id bigint, created_at timestamptz default now())
```

- Its role grant revokes update and delete, so it is append-only like
  `tool_calls`.
- Status is derived, never stored, so rows never change.

### 3. Status, derived from what already exists

`upload_status(conn, user, upload_id)` is owner-only and returns 404
otherwise. It joins `uploads` to `jobs`, to `documents` (the source plus
`external_id = s3_key`) and to `cases`, and returns one code:

| Code | Meaning |
|---|---|
| `queued` | the job hasn't run yet |
| `failed` | the job failed or the file would not convert; no error text is returned |
| `indexed` | the document is stored, but triage did not find a case study (a contract, proposal or deck), so no case was made |
| `in_review` | a draft case exists |
| `approved` | visible to staff |
| `rejected` | a reviewer rejected it |

- **What it never returns:** job payloads, error messages, document text or
  anyone else's uploads.
- **Unanswered:** whether an `indexed` contract is still useful (#213
  presale documents) is left to #213.

### 4. Portal: `/upload` for every user

- `GET /upload` (`require("user")`) shows the form, the types and the size
  cap, and the note "Visible to all staff after a reviewer approves it."
- It also lists **your uploads**: name, date and status, newest 50.
- `POST /upload` calls `accept_upload` and redirects back with a notice.
  - It keeps the guard's CSRF and Origin check: it is a normal portal form.
  - The guard's body cap for this path is `upload_cap()`, as for
    `/admin/upload`.
- The nav gets "Upload" when a staff source is configured.
- The review page shows **"Uploaded by <name>"** on cases whose document
  came from `uploads`, joined by key. No new column goes on `documents`.

### 5. MCP tools

| Tool | Hints | Behaviour |
|---|---|---|
| `upload_document(filename, size)` | not idempotent | Checks the name type, the size cap and the quota (without reserving). Returns `{upload_url, expires_in: 600, portal_url}`. |
| `get_upload_status(upload_id)` | read-only | `upload_status`, owner only |
| `list_my_uploads()` | read-only | the same 50 rows as the portal list |

- **The upload link.** `upload_url` is `{origin}/mcp/upload/{token}`. The
  token is itsdangerous with salt `"mcp-upload"`, holding `{k: user_key, n:
  safe name, s: size}` and valid for 10 minutes.
- **The PUT route.** `PUT /mcp/upload/{token}` takes **bearer tokens only**
  (`curl -T file -H "Authorization: Bearer …" <url>`), and these must all
  hold:
  - `k` equals the caller's key, otherwise 403
  - `Content-Length` equals `s`, otherwise 400
  - the body passes `accept_upload`
  - an expired or tampered token gives 410, after auth, as downloads do

  It returns `{upload_id}`. It shares the 60/min limit, and is audited in
  `tool_calls` as `upload`, without the token or the name. The access log
  masks the token, as it does for downloads.
- **Guard.** `/mcp/upload/...` gets the `upload_cap()` body cap. The CSRF
  skip already applies to `/mcp/*`, and is safe here because the route
  refuses cookies (decision below).
- **Humans in a browser** use `portal_url` (`/upload`), not the signed link.

## Alternatives rejected

- **Session or cookie auth on `/mcp/upload`.** The guard skips CSRF for
  `/mcp/*`, so a cookie-authenticated upload could be forged from another
  site. Downloads are GETs, so the same skip is harmless there. Uploads
  bearer-only, with the portal page for browsers. This narrows design
  section 4 ("or opens it in the browser").
- **Base64 in the tool argument.** It fills the model's context, and the
  MCP body cap is 1 MiB.
- **Queueing a whole-source crawl per upload** (today's admin path). It
  loses files that arrive while a crawl is running, and re-lists the bucket
  for every file.
- **A `documents.uploaded_by` column.** A join on the key gives the same
  thing with no crawl change.
- **SHA dedupe across users.** Two users uploading one file get two drafts,
  as today. Reviewers merge them with the existing tool. Stated plainly in
  `docs/mcp.md`.
- **Users deleting their uploads.** Not in this phase. A reviewer rejects
  them, or an admin removes them from the source.

## Risks

- **More people can feed the parsers.** docx, pptx and PDF parsing now
  takes files from every signed-in user, not just admins.
  - Bounded by: the magic check, the size cap, the quota, the corporate
    network (the ALB is internal) and parsing in the worker, not the web
    process.
  - Accepted for an internal tool. Codex is asked to look for parser-reachable
    paths.
- **Prompt injection in uploaded text.** It reaches the extraction LLM, as
  admin uploads do today. Output is a draft only, and a reviewer approves
  every case, so the reviewer gate is the control.
- **Storage growth.** Up to 200 MiB per user per day. The quota bounds it.
  S3 lifecycle rules are out of scope.
- **Visibility leaks before approval.** Search, `/go` and the MCP read tools
  already show approved cases only (`app/search.py:69,189`). A leak test pins
  that an uploaded draft is invisible to another plain user.

## Verification

- **`check_file`.** The admin route behaves as before: its existing upload
  tests stay green.
- **`accept_upload`:**
  - the quota by count and by bytes
  - a parallel burst stays within the quota (threads, under the lock)
  - a bad type, magic or size is refused
  - no staff source gives "not configured"
  - one `ingest_upload` job per upload, and it ingests that one key
- **Status:** each code reached from a seeded state; another user's id gives
  404; no error text leaks.
- **Portal:** `/upload` works for a plain user; the CSRF check still applies;
  the list shows only your own rows; the review page shows "Uploaded by".
- **MCP:**
  - schemas validate
  - `upload_document`, then PUT with a bearer token, then
    `get_upload_status` reaches `queued`
  - a cookie-only PUT gives 401
  - another user's token gives 403
  - a size mismatch gives 400
  - expired gives 410
  - the token is absent from logs and `tool_calls`
- **Leak test:** an uploaded draft appears in no other user's search,
  `get_case` or `/go`.
- **Append-only:** `update uploads` as `refs_app` is refused.
- **Smoke test:** on a local stack with `MCP_ENABLED=1`, upload a docx
  through the tool and the PUT, run the worker, and the status reaches
  `in_review` or `indexed`.
- **Reviews:** Opus and Codex, read-only.
- **Full suite:**
  `docker compose build app && docker compose run --rm app pytest`.
