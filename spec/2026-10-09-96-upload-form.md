# Spec: Admin upload form in the portal

Approved answers from the intent: the admin picks the source (Q2 b), the form
sits on each upload-source row (Q1 b), success is a 303 back to Sources with a
one-line notice for browsers (Q3 a), refusals show as HTML for browsers (Q4),
and the guard stays as it is, with the size limit shown next to the picker.

## Design

One route, one validation path. The existing `upload` route learns two things:
an optional `source_id`, and a browser branch at its two exits (success and
refusal). Everything else (type, size, magic bytes, role, guard) is unchanged
code.

### 1. `app/main.py`: tell a browser from an API client

Add one helper next to `upload_cap` (app/main.py:82):

```python
def wants_html(request: Request) -> bool:
    return "text/html" in request.headers.get("accept", "")
```

The 401 handler (app/main.py:133-138) uses it in place of its inline check at
line 136; behaviour unchanged. A browser form post sends `Accept: text/html,…`;
curl sends `*/*` and httpx/TestClient send `*/*`, so they stay on the JSON path.

### 2. `app/main.py`: the `upload` route (210-235)

- Signature gains `source_id: int | None = Form(None)` (import `Form` from
  fastapi, line 12). Absent → today's rule.
- Source lookup (lines 223-226) becomes one query:
  `select id, config, name from sources where kind='upload' and enabled
  and (%s::bigint is null or id = %s) order by id limit 1`.
  With `source_id` absent it is exactly today's lowest-id rule. With
  `source_id` present it matches only that source, and only if it is an
  enabled `upload` source; otherwise 404 `"no such enabled upload source"`
  (same wording and status as `crawl_now`, app/sources.py:126). Absent and
  none configured stays 400 `"no enabled upload source is configured"`.
- Refusals: the four `raise HTTPException(...)` calls (lines 216, 219, 221,
  226) and the new 404 go through one local `refuse(code, status, detail)`:
  for `wants_html(request)` it returns
  `RedirectResponse(f"/admin/sources?notice={code}", 303)`; otherwise it
  raises the same `HTTPException(status, detail)` as today. Codes:
  `type`, `size`, `content`, `nosource`, `source`.
- Success (line 235): for `wants_html(request)` return
  `RedirectResponse(f"/admin/sources?notice=uploaded&source={src[0]}&job={job_id}", 303)`;
  otherwise the same `JSONResponse({"job_id": job_id}, 202)`.
- Every value in a redirect URL is a fixed code or an integer from the
  database. The path is the literal `/admin/sources`. Nothing from the
  request (file name, headers, `source_id` as typed) is put in the URL.

### 3. `app/sources.py`: notices on the Sources page (52-57)

No notice or flash pattern exists in the portal (searched `app/` for notice,
flash, query_params: none). Smallest one, local to this page:

```python
NOTICES = {  # allow-list: the query string picks a message, never supplies one
    "uploaded": ("ok", "File queued for crawl"),
    "type": ("bad", "Upload refused: allowed types are .docx, .pdf, .pptx"),
    "size": ("bad", "Upload refused: the file is larger than the limit"),
    "content": ("bad", "Upload refused: the file content does not match its extension"),
    "nosource": ("bad", "Upload refused: no enabled upload source is configured"),
    "source": ("bad", "Upload refused: that source is not an enabled upload source"),
}
```

The type message is built from `UPLOAD_MAGIC` (import it from `app.main`, as
`require` already is) so the list cannot drift.

`sources_page` gains `notice: str = "", source: int | None = None,
job: int | None = None` query params. It passes `notice=NOTICES.get(notice)`
(unknown key → `None`, nothing shown), plus `job` and `source` only when the
notice is `uploaded`. The source name is looked up from the rows already
fetched (line 55) by id, so the page shows the stored name, never the URL.
It also passes `upload_cap=upload_cap()` and `upload_types=sorted(UPLOAD_MAGIC)`.

### 4. `app/templates/sources.html`

- Notice, just under the page head (after line 31), only when set:
  `<p class="badge {{ notice[0] }}" role="status">{{ notice[1] }}{% if job %}:
  job {{ job }}{% if source_name %} to {{ source_name }}{% endif %}{% endif %}</p>`.
  Reuses `.badge.ok` / `.badge.bad` (app/static/portal.css:44-46); no new CSS
  beyond what the plan finds it needs for spacing. Jinja autoescapes the name.
- Upload control, on each row where `kind == 'upload' and enabled`, next to
  "Crawl now" (line 44), as a `<details class="mini">` like Edit (45-58):

  ```html
  <details class="mini"><summary class="btn-sm" aria-label="Upload to {{ name }}">Upload</summary>
  <form method="post" action="/admin/upload" enctype="multipart/form-data">
  <input type="hidden" name="source_id" value="{{ id }}">
  <div class="field"><label for="u{{ id }}-file">File</label>
  <input type="file" id="u{{ id }}-file" name="file" required accept="{{ upload_types | join(',') }}">
  <span class="field-help">{{ upload_types | join(', ') }}, up to {{ upload_cap | filesizeformat }}.</span></div>
  <div class="action-row"><button class="btn primary">Upload</button></div>
  </form></details>
  ```

  No JavaScript. `accept` is a hint only; the server check is the gate.
  Disabled upload sources get no control (the route would refuse them).

## Alternatives rejected

- **Render sources.html directly with a 4xx on refusal.** Keeps the 4xx
  status, but the upload route would need the Sources page query and template
  context, which live in app/sources.py and import from app/main.py (a cycle).
  One redirect path for success and refusal is smaller.
- **Session flash message.** Works, but adds write-then-pop state to the
  session cookie for one page; the allow-listed query param is stateless and
  cannot carry input.
- **Echo the file name in the notice.** The intent asked for "which source";
  the file name is user input and would need to travel in the URL. Left out;
  the job id and source name identify the upload.
- **A separate browser-only route (e.g. `/admin/sources/{sid}/upload`).**
  Clean URL, but a second entry point to the same checks, and the guard's
  upload size cap is keyed on the path `/admin/upload` (app/main.py:126). One
  route keeps one cap and one validation path, as the intent requires.
- **Guard answers 413 as HTML.** Rejected in the intent: the guard stays
  untouched; the limit is shown next to the picker instead.
- **Form in the page head with a source `<select>`.** Q1 picked the row.

## Risks

- **ACL / wrong bucket:** `source_id` is admin-chosen input. The query filters
  `kind='upload' and enabled` along with the id, so an id of an `s3`,
  `sharepoint`, `confluence` or disabled source is refused, never written to
  its bucket. The route keeps `require("admin")`; other roles get 403 as now.
  Choosing between upload sources is the point: each has its own data class
  and access groups, which the crawl applies.
- **Open redirect:** both redirect targets are the literal `/admin/sources`
  plus a fixed code and integers; no `next`/`Referer` is used.
- **Reflected input:** `notice` only selects from `NOTICES`; unknown values
  show nothing. `source` and `job` are typed `int` (garbage → 422 from
  FastAPI, nothing rendered). The source name comes from the database and is
  autoescaped. A crafted link can at most show a false "queued" line with a
  real source name to an admin; it cannot inject text.
- **API compatibility:** curl/TestClient do not send `text/html`, so status
  codes and JSON bodies stay as today (tests/test_auth.py:57-149 unchanged).
  An API client that does send `Accept: text/html` would now get a 303; none
  in this repo does.
- **Guard:** unchanged. A browser multipart post sends `Origin` and
  `Content-Length`, so it passes (app/main.py:121-129). Oversize files still
  get the guard's JSON 413 in the browser; the limit beside the picker is the
  mitigation.
- **Refusal loses the 4xx status for browsers** (it becomes 303 + notice).
  Only for `text/html` requests; monitoring that counts 4xx on this path is
  API traffic only.

## Verification

New tests in tests/test_auth.py, reusing the `upload_src` fixture and the fake
`DOCX`/`PDF` bytes; invented names only (e.g. sources named with
`uuid.uuid4().hex`, files like `case-study.pdf`):

1. Browser success: post with `headers={"Accept": "text/html"}`,
   `follow_redirects=False` → 303, `Location` is
   `/admin/sources?notice=uploaded&source=<id>&job=<job id>`; object in S3;
   one `crawl_s3` job for that source.
2. `source_id` picks: two enabled upload sources, post `source_id` of the
   higher id → the job's `source_id` is that one (not the lowest).
3. ACL: `source_id` of an enabled `s3` source, of a disabled upload source,
   and of a missing id → 404 JSON for API, 303 `?notice=source` for HTML;
   no S3 object, no job.
4. Browser refusals: bad type, magic mismatch, oversize (via
   `UPLOAD_MAX_BYTES`), no upload source → 303 with `notice=type|content|size|nosource`.
5. Existing upload tests (tests/test_auth.py:113-150) pass unchanged.
6. Sources page (tests/test_sources.py): an enabled upload row has a form
   posting to `/admin/upload` with `enctype="multipart/form-data"`, the hidden
   `source_id`, and the size text; an `s3` row and a disabled upload row have
   none; `?notice=uploaded&source=<id>&job=7` shows the stored source name and
   job 7; `?notice=<script>x</script>` renders no notice and no `<script>`.
7. `pytest` green; manual: in the local demo stack, upload a made-up PDF from
   the "Demo: Bid library" row and see the notice and the job run.
