# Spec: Local demo with persistent made-up data

## Design

The approved intent answers: seed from pre-written case data, with live
extraction shown by uploading one more document; the host's Ollama is
optional and configured from a repo file; S3 persistence as the spec
shows works; outputs confirmed working (all five formats render
locally, checked on 2026-10-09); a separate compose project.

**One command: `scripts/demo.sh up | reset | down`** (bash, no new
dependency).
- `up`: `docker compose -p refsdemo -f docker-compose.yml -f
  docker-compose.demo.yml up -d --build web worker`, waits for
  `/healthz`, then runs the seed (idempotent), and prints the URL and the
  test users.
- `reset`: `down -v` for the `refsdemo` project only (its volume), then
  `up`. This is the deliberate way back to the original demo set.
- `down`: stops the project and keeps the data.
- It reads `.env.demo` from the repo (committed, no secrets): the model
  settings for the host's Ollama (`ollama_chat/qwen3:14b`, `api_base
  http://host.docker.internal:11434`, `destination: local`). If Ollama
  doesn't answer at `localhost:11434`, it starts without models and says
  what needs one. Nothing outside the repo and Docker is read or written.
- The project name `refsdemo` keeps demo data apart from a developer's own
  local stack. Ports stay `127.0.0.1:8000` and `127.0.0.1:8080`, so only
  one of the two runs at a time; the script says so if the port is taken.

**`docker-compose.demo.yml`** (an override; the base file and CI are
unchanged):
- `db` gets a named volume `pgdata` at `/var/lib/postgresql/data`, so the
  data survives `down` and `up`.
- `web` and `worker` get `env_file: .env.demo` (optional through
  `required: false`, so a missing file isn't an error).

**S3:** moto keeps objects in memory. Rather than add a new S3 server,
the seed **re-puts every demo original from the repo on each `up`**
(`put_object` is idempotent). So review, re-extraction and the stored
originals keep working after a restart. Uploads made during a demo are
lost on restart; the README says so.

**Seed: `scripts/seed_demo.py`** (runs inside `web` with `docker compose
exec`, so it uses the app's own code and settings):
- **Inputs, all made up, under `demo/`:**
  - `demo/docs/*.docx`: 10 to 12 short case studies and 2 contracts (SOW
    and change order of one engagement, to show #52, #55 and #64), using
    fictional company names (Contoso, Northwind, Fabrikam, Woodgrove,
    Tailspin, Litware, Adventure Works and similar);
  - `demo/cases.json`: for each document, the pre-written `ReferenceCase`
    (title, client mention, industry, region, lists, outcomes with real
    metric names, quotes copied verbatim from the document) and the
    target status;
  - `demo/registry.json`: clients with aliases, labels, referenceable and
    logo flags, so both named and anonymised outputs show;
  - `demo/sources.json`: two upload sources with different access groups
    (`sales` and `delivery`), so need-to-know shows.
- **For each document:** put the original to S3 under its source's
  prefix, convert it with `ingest.to_markdown()` (Docling, no LLM), insert
  the document row, insert the case from `cases.json`, then run the app's
  own `check()`, `fix_summary()` and `search_text()`, so a seeded case
  carries exactly the flags real extraction would give it. A case whose
  quote isn't in its document is shown as unsourced, never faked.
- **Statuses:** most cases approved; about 3 left in review, so a reviewer
  has a queue (one with a fixable outcome, one with an unsourced field);
  one engagement pair ready to merge (#55).
- **Idempotent:** keyed by `(source name, external_id)`. A second run
  re-puts the S3 objects and leaves existing rows alone. It never touches
  rows it didn't create.

**README `## Local demo`:** the three commands, the test users (from
`## Local login`), what needs a model, and a walkthrough:
1. `sales`: search a pasted bid, download Word, PowerPoint and PDF, see a
   non-referenceable client anonymised;
2. `reviewer`: review the queue, fix an outcome, approve; merge the two
   contracts;
3. `admin`: sources, access groups, the client registry, the "add to
   registry" note, the audit log;
4. with a model: upload one more document from `demo/docs/extra/` and
   watch it reach the review queue;
5. `nobody`: gets 403.

## Alternatives rejected

- **Extracting the demo documents with the model at first start**
  (intent question 1b): slow on CPU, needs a model, and the result
  varies, as today's case-1 title and "metric" names showed.
- **An Ollama container in compose** (question 2b): a multi-GB download,
  slow on CPU.
- **MinIO or another S3 server with a volume:** a new image and service,
  when re-putting the originals from the repo is enough.
- **A volume on `db` in the base compose file:** it would change every
  developer's and CI's database lifetime; the override keeps it demo only.
- **SQL dumps as the seed:** they'd skip the app's own `check()`, and break
  silently when the schema changes.

## Risks

- **Ports taken by a developer's own stack:** the script checks and
  stops with a message.
- **Schema changes** after the seed was written: the seed goes through
  `ReferenceCase` and `db.init()`, so a mismatch fails loudly at seed
  time. A seed test (below) catches it in CI.
- **Made-up names that collide with real clients:** only well-known
  fictional names are used; review checks the list.
- **The extraction-prompt weakness** (outcomes named "metric") shows in
  the live-upload step. That's honest, and it's tracked as its own issue.

## Verification

- `tests/test_seed_demo.py`: runs the seed against the test database with
  a stubbed S3 (moto, as `test_ingest.py` does). Every seeded case
  validates, the planned ones are sourced, the counts per status match
  `cases.json`, and a second run adds nothing.
- Manual: `scripts/demo.sh reset` on this workstation, then the README
  walkthrough as each user. Then `down`, `up`: the data and originals are
  still there.
- CI unchanged: `docker compose build && docker compose run --rm app
  pytest`.
