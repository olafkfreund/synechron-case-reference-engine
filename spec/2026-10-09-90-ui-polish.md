# Spec: Portal UI that is professional, modern and easy to use

## Design

Approved intent answers:
- **staged**, in five stages, with the demo reloaded after each;
- **Word** as the one visible download;
- a **second Codex check**, read-only, on new screenshots before the PR.

The design follows the Codex review in
`docs/reviews/2026-10-09-90-codex-ui-review.md`.

**Rules for every stage.**
- Templates and `app/static/portal.css` only. A route may pass an extra
  display-only value it already computes, but there are no new queries,
  routes, form `name`s or `value`s, and no access changes.
- No JavaScript: `<details>`/`<summary>` for disclosures, and plain forms.
- Inline SVG icons from one Jinja macro file, `app/templates/_icons.html`
  (`{% macro icon(name) %}`), stroke-only, 20px, `aria-hidden="true"`.
  The set: search, globe, inbox, users, database, shield, clock, file,
  check, alert.
- Every input gets a visible `<label for>`. Repeated buttons and
  checkboxes get row context in their accessible name (`aria-label="Save
  Demo: Bid library"`, `"Referenceable: Contoso"`), while the visible text
  stays the same, so tests that match button text keep passing.

**Shared components (stage 1).** In `portal.css`, beside the existing
tokens:

| Class | Purpose |
|---|---|
| `.page-head` (+ `.page-head-actions`) | h1, a one-line intro in `.muted`, status chips and the primary action on one row, wrapping on narrow screens |
| `.stat-grid` / `.stat-tile` | 2–4 tiles: a big number, a label and an optional icon |
| `.section-card` / `.card-head` | a card whose head row holds a title, chips and actions |
| `.empty-state` | a centred icon, a line, and one next step |
| `.field` / `.field-help` | a label above its input, with small help text below |
| `.action-row` | the primary action right, secondary actions left; wraps |
| `.detail-panel` | `<details>` with a 44px `<summary>`, a chevron and a tinted body |
| `.status-list` | `dl`-style key/value pairs for counts and config |
| `.avatar` (existing) | reused for client initials in content |

- **Checkboxes:** each checkbox sits in a `<label class="check">` with a
  44px hit area.
- **Header:**
  - `.site-header-in` gets two intentional rows at widths under 1500px:
    brand and user on row 1, tabs on row 2, with no orphaned wrap;
  - the role string is shortened to the highest role (`admin`,
    `reviewer`, `user`) in the header, while the full list stays in the
    `title` attribute.

**Stage 2: home and search.**
- `landing.html`:
  - a lead card for "Find reference cases" (icon, title, line, primary
    button-styled link) with a Research card beside it;
  - a "Needs review" card for reviewers;
  - the four admin links as a compact 2×2 grid of small cards.
- `search.html`:
  - labelled filters in a row;
  - result cards with a head (title, client label with avatar initials,
    basis chip), "Why it fits", outcomes as a check-icon list, and the
    suggested-wording inset titled "Suggested wording · not in
    downloads";
  - an `.action-row` with **Download Word** (primary, the existing
    `name="format" value="docx"` button), a `.detail-panel` "Other
    formats" holding the other four existing buttons, and "Research this";
  - `.empty-state` when nothing matches.
  - "Other matches" become compact rows with a basis chip.

**Stage 3: review.**
- `review_list.html`:
  - three stat tiles (awaiting review, needs attention, due soon),
    counted in the template from `cases`/`due_soon`;
  - a table with the title linked, a "Review case" link-button, chips only
    for counts that aren't zero, and the document as secondary text;
  - one calm line when nothing is due soon.
- `review_detail.html`:
  - a `.page-head` with the case title (fallback "Case N") and status and
    basis chips;
  - a metadata `.status-list` card (document, source, external id,
    members for merged cases);
  - notes and the add-to-registry form as before;
  - the field table split into "Needs attention" (unsourced or empty)
    then "Fields", by looping over `rows` twice with a filter. Row form
    ids are unchanged; the forms stay outside the tables. Each quote is a
    tinted panel;
  - a final action card: "Approving empties unsourced fields" warning,
    Approve (primary), Reject or Un-merge.
- `review_merge.html`: the same page head and cards.

**Stage 4: admin.**
- `sources.html`:
  - a `.page-head`, with the three policy paragraphs moved into
    `.detail-panel`s ("Data classes", "Contracts executed", "Access
    groups");
  - one `.section-card` per source: a head with name, kind chip,
    enabled/disabled chip and data-class chip (full word), last run, and a
    3-number `.stat-grid` (new, skipped, failed);
  - a `.detail-panel` "Edit and run details" holding the full-width
    labelled access-groups input, the data-class select, the enabled and
    contracts-executed checks, config as a `.status-list` (not raw JSON),
    all counts, and the Save / Crawl now `.action-row`;
  - the existing `s{id}` forms and field names are unchanged;
  - "Add source" as a card with labelled fields, and the config examples
    as `.field-help` per kind.
- `clients.html`:
  - one row per client: avatar initials, name, label, and
    referenceable/logo chips;
  - a `.detail-panel` "Edit" with labelled fields;
  - Delete inside its own small `.detail-panel` "Delete…" on eligible rows
    only (the forms are unchanged);
  - the alias guidance in a "How aliases work" panel.
- `models.html`: an `.empty-state` when there are no approvals, a
  read-only "Data class: Confidential" line, and labelled fields.
- `audit.html`: titled "Audit activity", with four summary tiles, each
  section as a card with its own empty line, chips for yes/no, a
  labelled, bounded user filter, and labelled Newer/Older links.

**Stage 5: research.**
- `research.html`: a narrower card with a "Your research question" label,
  the Ask → Preview → Send steps, and a privacy line with a disclosure.
- `research_preview.html`: the exact query in a bordered mono panel
  directly above Send and Cancel.
- `research_view.html`:
  - claims as source cards (quote, publisher, date, type chip);
  - comparison stays a table;
  - downloads in a final card with a visible label.

**Second Codex check (after stage 5):**
- **Input:** read-only, on fresh screenshots of the demo, against the
  review's findings.
- **Output:** findings go into the plan; fixes the user agrees to are
  made in this PR.
- **Who:** Codex never edits; the `coder` agent writes the code.

## Alternatives rejected

- **A CSS framework or icon font:** a new dependency or a network fetch.
- **Small JavaScript for tabs and "show more":** against the no-JS
  constraint; `<details>` covers it.
- **Codex implementing:** the org policy has the `coder` agent write
  approved plans. Codex reviews.
- **One big change:** staged delivery lets the user see progress in the
  demo and keeps each review small.

## Risks

- **Tests that match markup:** button texts, `form="fN"`, `value=`, `'value="remove"'`
  and `"<tr>\n<form" not in page` are kept. Any test that still breaks is
  updated with the change and listed in the plan.
- **`<details>` hiding required inputs:** a required field inside a closed
  disclosure blocks submit with no visible error. Inputs in edit panels
  are not `required`, and the server validates them as today.
- **Counting in templates:** only simple `selectattr`/`length` on lists the
  route already passes; nothing that needs a query.
- **Header at odd widths:** checked at 1280, 1440 and 390px.

## Verification

- The full suite after each stage:
  `docker compose build app && docker compose run --rm app pytest`.
- `tests/test_ui.py` extended:
  - every page still has no `<script`;
  - every `<input>`, `<select>` and `<textarea>` with a `name` has a
    `<label for>` or a wrapping `<label>`, checked by parsing the rendered
    HTML with `html.parser`;
  - search results carry exactly one visible `value="docx"` outside
    `<details>`.
- Headless Chromium screenshots of every page at 1440 and 390px on the
  demo data, before and after, attached to the PR.
- The second Codex check, read-only, with its findings in the plan.
