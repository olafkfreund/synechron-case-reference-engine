# Spec: The demo shows complete case studies

## Design

The work is all data plus one change to how the seed script works. The app
code is unchanged.

### 1. Data: `demo/cases.json`

The file keeps its shape: `sources`, `clients`, `cases`, and per case
`source`, `file`, `paragraphs`, `status` and `case`. Two things change:

- **`paragraphs`.** Each document grows from about 12 one-line sentences
  (median 570 characters) to **600 to 1,200 words** of plainly fictional
  text, in this order:
  1. title
  2. client situation and drivers
  3. scope and deliverables
  4. delivery approach and phases (with team and duration)
  5. configuration and integrations
  6. technical references (standards, interfaces, product versions)
  7. outcomes with named metrics
  8. lessons learned (delivered work only)
- **`case`.** Each case also carries:
  - **`points`:** 3 to 6 per section for challenge, solution, implementation
    and configuration. Each one is `{value, source_quote}`.
  - **`prose`:** for the same four sections,
    `{text, by_reviewer: true, flags: []}`. The text is 80 to 200 words and is
    built only from that section's point values.
  - **`tech_references`:** see section 4.
  - **`outcomes`** with real metric names, never "metric".
  - **`period`**, `duration_months` and `team_size`.

  `extraction_version` isn't written by hand: the seed stamps
  `EXTRACTION_VERSION`.

The prose is marked `by_reviewer: true` because no model wrote it; it is
fixed demo text. That means approval and outputs use it as is, and
re-extraction keeps it (the #198 rule).

**Who writes it:** a coder agent writes the fictional text. It uses only the
10 existing fictional names (Contoso, Northwind, Fabrikam, Woodgrove,
Tailspin, Litware, Adventure Works, Wide World Importers, Proseware and
Alpine Ski House) and generic products (Kafka, PostgreSQL, Kubernetes and
the like). It uses no real banks, people, places beyond country or region,
or deal values.

### 2. A completeness mix that shows every state

These are worked out against `app/completeness.py` (9 items: challenge and
solution at 80 words or more, implementation, configuration, at least 3
capabilities, at least 3 technologies, results, period, diagram).

| Group | Cases | Target |
|---|---|---|
| Complete | the 9 approved delivered cases, minus Litware citizen portal | 9/9: every item, including one seeded diagram |
| Deliberately partial | Litware citizen portal (approved) | 6/9: no diagram, no configuration, 2 technologies, approved with a seeded override reason so the Audit page shows an example |
| Waiting for review, clean | Northwind loyalty, Litware records archive | 8/9, no diagram yet, with a seeded diagram candidate to show "Use" |
| Waiting for review, flagged | Contoso fraud scoring | Solution prose is model-style (`by_reviewer: false`) with one flag, e.g. "names 'Snowflake', which no quote supports", to show the approval block |
| Engagements | Fabrikam SOW and change order | contracted scope: no outcomes or lessons, and the merge flow kept |

**The diagram.** One simple box-and-arrow PNG per complete case, drawn at
seed time with Pillow (already installed): three or four boxes labelled with
that case's own technologies, connected by arrows. No image files are added
to the repository. It's stored through the normal `diagrams` table as
`ready`, with a caption. The Northwind loyalty and Litware records cases get
a `document_images` candidate the same way.

### 3. The refresh rule

`seed_demo.py` changes from "insert once, then skip" to "insert or update":

- It still touches only the sources named in `demo/cases.json`, all of which
  are prefixed `Demo:`, and their own `external_id`s. Every write is keyed on
  `(source_id, external_id)` of a demo source. It never runs a query without
  a source id.
- **A changed document** (its checksum differs from the row's): update the
  document's text, checksum and `updated_at`, and update the case data in
  place. The status goes back to the file's `status`, and approved cases are
  re-stamped `approved_by='demo-seed'`. The `diagrams` and `document_images`
  rows for that case or document are replaced.
- **An unchanged document:** do nothing. It's idempotent, as
  `test_seed_twice` already requires.
- **Never deleted:** rows for a demo case that's no longer in the file.
- **The S3 originals** are put again every run, as today.

### 4. Ordering with #212 D: `tech_references`

**Choice: seed them only once #212 phase D is merged.** This PR goes after
#212 D. `tech_references` is written straight into `case`, with no guard.
Before D merges, `ReferenceCase` (with `extra="forbid"`) would reject the
key, and the seed test fails fast. A guard would be code nobody needs once D
lands.

### 5. Hard checks at seed time

Before writing anything, for every case:

1. Every `source_quote` (headline fields, points, list items, outcomes,
   period, references) is in its document text after `to_markdown`, using
   `schema.quote_in`. If one is missing, the script exits non-zero and names
   the case file and the field. It never writes a partial seed.
2. `check(case, text)` leaves no item `unsourced`.
3. `check_prose` gives no flags on `by_reviewer` prose. The one flagged
   example is the deliberate exception, and is marked in the file.

## Alternatives rejected

- **Have the local model extract the new documents at seed time.** That
  makes the demo need Ollama, takes minutes, and gives different output on
  each run. The intent says no model calls.
- **Add diagram image files to `demo/`.** That means binary files in the
  repository, for a picture Pillow can draw in a few lines.
- **Wipe and re-seed the demo sources.** That loses the IDs, the review
  history and the user's own test approvals. Updating in place keeps them.
- **Guard `tech_references` so this can ship before D.** That's code that is
  dead the day D merges. Ordering after D is free.

## Risks

- **Refreshing overwrites the demo cases' review state.** For example, a demo
  case the user approved by hand goes back to the file's status. This only
  affects `Demo:` sources and is the point of a refresh. The README says so.
- **Real-looking names in hand-written text.** Covered by the fictional-names allow-list test
  below and by review of the diff.
- **A large `cases.json`.** About 14 × 8 KB, around 120 KB of JSON. That's
  fine.

## Verification

- **`tests/test_seed_demo.py`:**
  - Seeding twice adds no rows (this test exists today).
  - **Refresh:** change one document's paragraphs in a copy of the data,
    seed again, and check that the case and document are updated, other
    sources are untouched, and a non-demo source with the same `external_id`
    is untouched.
  - **Every quote is found** in its text, for every case. This is a
    data-only test with no database.
  - **Only fictional names (decision, 2026-10-13):** every case's
    `client_mention` and `organisations`, and every capitalised multi-word
    name in the paragraphs that looks like an organisation, must come from
    the demo's own `clients` list (names and aliases) or a short fixed
    allow-list of vendor and product names (for example ServiceNow, Kafka,
    Azure). An allow-list is simpler and stricter than a hashed deny-list,
    and it needs no list of real names in the repository.
  - **Completeness:** every case scores what section 2 says. Complete cases
    score 9/9, Litware citizen portal 6/9, the clean review cases 8/9, and
    Contoso fraud has 1 flag.
- **By hand,** with `scripts/demo.sh up` on the existing demo:
  - Search shows "Complete" on 8 cases.
  - The Contoso fraud preview shows four paragraphs per section.
  - The Audit page shows one override.
  - The user's presale source and cases are unchanged.
