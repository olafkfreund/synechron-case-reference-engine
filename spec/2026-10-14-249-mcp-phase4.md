# Spec: MCP server, phase 4 (reviewer tools)

Phases 1–3 gave every signed-in user read, generate, research, library,
brief and upload tools over MCP. Phase 4 adds the decision recorded in the
design (`docs/mcp-design.md`, Tool catalogue): **reviewers can read and edit
draft cases from an approved AI client. Approval stays in the portal.** There
are no approve, reject, merge or diagram tools.

## The decision this spec needs from you: un-anonymised data to the AI client

The general tools only ever return the anonymised view (`protect()`, `/go`
links). A reviewer, by contrast, works on the **raw draft**: client names,
quotes copied word for word from confidential documents, and the
document's own wording. Every `edit_case` quote must match the document
exactly (`quote_in`), so an anonymised view cannot be edited. A quote
showing "a US regional bank" where the document says "Comerica" would turn
every saved field "unsourced".

Reviewer tools therefore send **confidential data to the AI client's
model**, which the data policy treats as a `third-party` destination
(`app/llm.py:50-78`). Today that needs an admin approval in
`model_approvals`, with an expiry, for each model and data class.

**Recommended:** treat an approved review client the same way the portal
treats an approved model.
- **Approval.** An admin approves the client in `/admin/models` as
  `mcp-client:<azp>` for `confidential`, with an expiry. That is the
  existing table, page, audit and expiry, with nothing new to learn.
- **No approval row, no reviewer tools.** A client without a live
  approval cannot use them, even with the `refs.review` scope.
- **One gate.** This replaces the design's separate `MCP_REVIEW_CLIENT_IDS`
  environment variable, so there is only one control.

**Alternative (rejected unless you prefer it):** reviewer tools return the
anonymised view and accept quotes only as references to stored points (no
free-text quotes). That is safer for data, but a reviewer then can't fix a
wrong quote from the agent, which is most of the value.

## Design

### 1. Who may call the reviewer tools (checked on every call, in this order)

1. The usual phase 1 gate: a valid token, the `refs.access` scope, an
   approved `azp`, and the user's groups. This covers the user's
   **reviewer** role (`roles_for`), the same as `require("reviewer")`.
2. **The `refs.review` scope** in `scp`. Entra pre-authorises it only for
   review-approved clients. A missing scope gives a tool error naming the
   scope, so the client can sign in again with it.
3. **A live `model_approvals` row** `(model='mcp-client:<azp>',
   data_class='confidential', expires_at > now())`, as decided above.
4. **The same case visibility as the portal reviewer.** `load()` checks
   `VISIBLE` and `OPEN`, giving 404 when hidden and 409 when changed or
   closed (`app/review.py:87-104`).

Refusals are audited in `tool_calls`, as in phases 1–3. The tools stay
listed for everyone, because the server is stateless, but a non-reviewer
gets the portal's "reviewer role required".

### 2. Lift the edit route into a service function

`review.apply_edit(conn, user, cid, v, field, value=None, metric=None,
start=None, end=None, quote=None, written=False, action="save") -> new_v`
is lifted from `POST /review/{cid}/edit` (`app/review.py:274-366`).
- **Same body.** The route becomes a thin wrapper. The behaviour stays
  identical: `load`, `check`, prose flags, and an approved case returning
  to `extracted` on any change.
- **Tests.** The existing edit tests stay unchanged and green.

### 3. Tools (phase 1 wrapper: audit, 60/min, untrusted preface, portal error text)

| Tool | Hints | Returns |
|---|---|---|
| `list_review_queue(page?)` | read-only | `reviewable_cases` rows: id, title, status, action-note count, unsourced count, review due. Same rows as `/review`. |
| `get_review_case(case_id)` | read-only | the **allow-listed** view (below) plus `v` |
| `edit_case(case_id, v, field, value?, metric?, start?, end?, quote?, written?, action?)` | not idempotent | `apply_edit`, returning the new `v`, the field's new sourced or unsourced state, and its flags (prose) |

**`get_review_case` field allowlist.** Only these fields leave the server:

| Field | Contents |
|---|---|
| `case` | id, status, basis |
| `fields[]` | label, path (`tech_stack.3`), value(s), quote, sourced, unsourced or written flag |
| `prose{}` | per section: text, flags, written by reviewer |
| `notes` | action notes only (`split_notes`) |
| `completeness` | each check with its detail |
| `document` | title only |
| `v` | the version for the next edit |

**Never returned:**
- `documents.text`
- `external_id` (paths name the client, for example `…/Comerica/…`)
- source URLs
- other cases
- uploader identity
- public research sources

**Not in phase 4:**
- approve, reject, merge, unmerge
- architecture and diagram edits
- the client registry

These stay in the portal.

### 4. Mock IdP and docs

- **Mock IdP.** The `refs-mcp` issuer can mint a token with `scp: "refs.access
  refs.review"` for a reviewer. Run `scripts/mcp_token.sh reviewer
  refs-reviewers --review`.
- **Demo seed.** It adds a `model_approvals` row for the dev client id, with
  a 30-day expiry.
- **`docs/mcp.md` gets a "Reviewing from an AI client" section:**
  - the approval step in `/admin/models`
  - what data leaves (the allowlist above)
  - what stays in the portal
  - the 409 "case changed" retry: fetch the case again, then edit with the
    new `v`

## Alternatives rejected

- **A separate `MCP_REVIEW_CLIENT_IDS` environment variable** (the
  original design). It is a second control, with no expiry, audit or
  admin UI. The model-approval row covers the same need.
- **Anonymised reviewer view with free-text quotes.** Quotes would never
  match the document. See the decision above.
- **Approve over MCP.** Excluded by the approved design. Approval is a
  human judgement in the portal.

## Risks

- **Confidential text in the client's model context.** This is bounded by
  the per-client approval with expiry, the field allowlist, and the
  `tool_calls` audit (ids only). This is the data-policy decision above.
- **Concurrent edits.** These are caught by the `v` lock, as in the
  portal: 409, then fetch again.
- **Prompt injection from document text** in quotes and prose. It is
  wrapped in the untrusted preface. The agent's edits are checked against
  the document the same way a human's are, and a person still approves.

## Verification

- **Lift.** `tests/test_review*.py` stays unchanged and green. `apply_edit`
  through MCP and the route give identical case JSON for the same edit.
- **Gate tests**, each giving the portal's refusal and an audit row:
  - a user who isn't a reviewer
  - a token without `refs.review`
  - an approved `azp` but no `model_approvals` row
  - an expired approval
  - a hidden case (404)
  - a stale `v` (409)
- **Leak test.** `get_review_case` output contains none of
  `documents.text`, `external_id`, source URLs or another case's data.
- **Edit tests:**
  - a list item save and remove
  - a prose edit returns its flags
  - an approved case returns to `extracted`
  - a quote not in the document comes back unsourced
- **Schemas** validate. The tool-set assertion goes to 20.
- **Smoke test** on a local stack with `MCP_ENABLED=1`: a reviewer token
  with `refs.review`, then `list_review_queue`, `get_review_case`, and
  `edit_case` on a demo draft, which gives the new `v`.
- **Reviews:** Opus, Codex and agy, read-only.
- **Full suite:**
  `docker compose build app && docker compose run --rm app pytest`.
