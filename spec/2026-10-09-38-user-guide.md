# Spec: User guide for bid team, reviewers and admins

## Design

Short, task-based Markdown pages in the repo, one per role plus an index, describing the UI merged
on main in PR #94. Each task section has three parts: **What it's for**, **Steps**, **What you see**.
Every button, label and heading is quoted exactly as `app/templates/*.html` renders it, in **bold**,
so a check can find it (see Verification). No change to `app/`, routes, templates or tests other
than the label check.

### Files

```
docs/user-guide/
  README.md          index
  bid-team.md        user role
  reviewers.md       reviewer role
  admins.md          admin role
  img/*.png          screenshots (list below)
scripts/guide_screens.sh   makes the screenshots from the demo
tests/test_user_guide.py   link check + label check
README.md                  one line under "## Links": the user guide
```

### `README.md` (index)

- What the portal is for, in two sentences.
- **Which page is mine:** the role comes from your groups. Admins also have the reviewer and user
  roles, reviewers also have the user role (`roles_for()` in `app/main.py`), so admins and reviewers
  read the bid-team page too.
- The tabs each role sees (from `app/templates/base.html`):
  user **Find references**, **Research**; reviewer adds **Review queue**; admin adds **Sources**,
  **Client registry**, **Model approvals**, **Audit**.
- Logging in and **Log out**; someone with no role sees no tabs and should ask an admin.
- Links to the three role pages.

### `bid-team.md`

1. **Log in and find your way:** landing page **Customer reference engine** with **Find reference
   cases**; the tabs.
2. **Search:** page **Find reference cases**; fields **Bid context**, **Industry**, **Region**,
   **Technology**; button **Search**. How ranking works in plain words (best matches first, then
   **Other matches**). Only cases from sources your groups can see appear.
3. **Read a result:** title, client label, the fields shown.
4. **Download:** **Download Word**; **Other formats** opens **(Markdown)**, **(PDF)**,
   **(PDF slides)**, **(PowerPoint)**, **(Word)**. Which format suits which use.
5. **Research (public sources):** from a case, **Research this (public sources)**; or the
   **Research** tab, page **Online research**, field **Your research question**, button
   **Preview the search query**. The preview page **Send this search?** shows exactly what leaves the
   portal; **Send** or **Cancel**. The result page **Research** has **What public sources say**,
   **Comparison**, **Sources**; "source(s) skipped" means a page could not be used.
6. **Download with industry context:** section **Download with an "Industry context" section**,
   **Format** (**Word**, **PDF**, **PDF slides**, **PowerPoint**, **Markdown**), **Download**.
   With no case picked, the box **I understand the industry context section contains public
   statements by third parties, not our delivery evidence** must be ticked, and why: public
   statements are never presented as our delivery (`app/render.py:356`).

### `reviewers.md`

1. **Review queue:** page **Review queue**; **Awaiting review**, **Due for re-review within 30
   days**; the **unsourced** count badge; **Review case**.
2. **Sourced and unsourced:** badges **sourced** / **unsourced**; **Needs attention** lists the
   unsourced fields first; **Source quote** is the text from the document that backs a field.
   A field with no quote is unsourced.
3. **Edit fields:** **Fields**, edit, **Save**.
4. **Add and remove list items** (capabilities, technology, outcomes): **Add**, **Remove**.
5. **Approve or reject:** **Decision**; the warning "Approving empties every unsourced field. Check
   the quotes first."; **Approve (unsourced fields are emptied)**; **Reject**.
6. **New client:** **Add as client** when the case names a client not in the registry.
7. **Merge and un-merge:** **Merge with other contracts for the same client**, **Preview merge**;
   page **Merge contracts** with **Differing fields**; **Merge**. **Un-merge (the contracts go back
   to the queue)**.
8. **Re-review:** when an approved case comes back (it appears under **Due for re-review within 30
   days**) and what to check.

### `admins.md`

1. **Sources:** page **Sources**; **+ Add source** with **Name**, **Kind**, **Config (JSON)**,
   **Data class**, **Access groups**; **Add source**. **Edit**, **Save**. Help panels
   **Access groups**, **Data classes**, **Contracts executed** (what ticking it does, quoted from the
   page). Which files a crawl skips (permissions differ from the site root, restricted Confluence
   pages).
2. **Crawl:** **Crawl now**; **Last run counts** New / Skipped / Failed and what to do about each.
3. **Upload:** there is no upload form; uploads go through `POST /admin/upload` to an upload source
   (config `{"bucket": "…", "prefix": "…"}`). One short example, made-up file name.
4. **Client registry:** page **Client registry**; **+ Add client** with **Name**, **Label in
   outputs**, **Aliases (one per line)**; **Add client**; **Edit**, **Save**; **How aliases work**;
   **Delete…**, **Delete** (only while no case uses the client).
5. **Model approvals:** page **Model approvals**; **Approve a model** with **Model id**,
   **Expiry date**, **Note**; **Approve**; **Revoke**; the **Status** and **Expires** columns.
6. **Audit:** page **Audit activity**; **User (exact sub)**, **Filter**; sections **Generated
   outputs** (incl. **Industry-only ack**), **Model approvals**, **Access group changes**,
   **Source data class changes**; **« newer** / **older »**.

What each role can do only; no access-check internals.

### How screenshots are made

`scripts/guide_screens.sh`, run by hand against a running demo (`scripts/demo.sh up`, project
`refsdemo`, made-up data). It never starts or stops compose.

1. Log in each demo user through the mock IdP with curl and a cookie jar, as
   `scripts/check_local_login.sh` does, using the demo claims from `scripts/demo.sh`.
2. Fetch each page with that jar (posting the search form for `search.png`), add
   `<base href="http://localhost:8000/">` so `/static` CSS and fonts load (they are public), and save
   it to a temp file.
3. `chromium --headless --window-size=1280,900 --screenshot=<file> file://<temp>`. The pages have no
   script, so a saved page renders the same.

Refuses to run unless `BASE` is `localhost`. Chromium is already on the dev machine; no new
dependency.

### README link

One line under `## Links` in the top-level `README.md`: `[User guide](docs/user-guide/README.md)`.

## Alternatives rejected

- **Help page served by the portal:** needs routes and templates and a deploy to change text.
  The repo is reviewed like any change; a portal link can come later.
- **One long guide:** each reader would wade through tasks they cannot do.
- **One screenshot per task, or none:** per task goes stale fast; none leaves readers unsure which
  page they are on.
- **Playwright or Selenium for screenshots:** a new dependency for eight images. The pages have no
  JavaScript, so saved HTML in headless Chromium is enough.
- **Screenshots from refsdev or a real deployment:** could show real clients; the repo is public.

## Risks

- **The UI changes and the guide drifts.** A renamed button breaks a reader's steps. Mitigation:
  the label check fails CI when a bold label is no longer in any template, and the PR template
  habit is that a template change updates the guide. Screenshots can still go stale silently;
  re-run `scripts/guide_screens.sh` when a main page's layout changes.
- **The repo is public, so made-up data only.** No client names, people, hosts or URLs except
  `localhost` and the demo's fictional companies. Screenshots come only from `refsdemo`; the script
  refuses any non-localhost `BASE`. Review looks at every image before merge.
- **Upload has no UI.** The admin page documents an API call; if an upload form is added later,
  the section changes.

## Verification

- `tests/test_user_guide.py`, run in the normal test suite:
  - **Link check:** every relative Markdown link and image in `docs/user-guide/*.md` and the
    README guide link points to a file that exists.
  - **Label check:** every `**…**` span in the guide pages, after dropping a known list of
    non-label emphasis, appears verbatim (HTML entities decoded, Jinja `{{ … }}` parts treated as a
    wildcard) in `app/templates/*.html`.
- Manual: run `scripts/demo.sh up` (the user, not the agent), then `scripts/guide_screens.sh`;
  eight PNGs appear, each shows the expected page and only demo data.
- Read-through: each role page followed step by step against the demo as that user.
