# Spec: Speed up CI with build caching

## Design

One file changes: `.github/workflows/ci.yml`. The Dockerfile and
`docker-compose.yml` stay as they are.

The approved decisions:
1. Build the image with buildx and cache it in the GitHub Actions cache.
2. Load the result as the image that compose uses for `app`.
3. Run `push` CI only on `main`.
4. Use GitHub's own cache scoping: per branch, falling back to `main`.
5. Leave postgres out of scope.

### The workflow

```yaml
name: ci
on:
  push:
    branches: [main]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    env:
      # fixes the compose image name for `app` to refs-ci-app (compose names it <project>-<service>)
      COMPOSE_PROJECT_NAME: refs-ci
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v4
      - uses: docker/build-push-action@v7
        with:
          context: .
          tags: refs-ci-app:latest
          load: true
          cache-from: type=gha
          cache-to: type=gha
      - run: docker compose run --rm app pytest
```

Line by line, against today's `ci.yml`:

- **Trigger** (`ci.yml:2`, `on: [push, pull_request]`). This becomes
  `push` on `main` plus every `pull_request`. A PR branch then gets one run
  per push, not two. Branches without a PR get no CI until a PR is opened,
  as approved. The job is still called `test`, so the required check for
  #51 keeps its name.
- **Builder** (`setup-buildx-action@v4`). The default `docker` driver can't
  export a cache to `type=gha`, so this creates a `docker-container`
  builder.
- **Build** (`build-push-action@v7`, replacing `ci.yml:8`
  `docker compose build`):
  - `context: .` builds from the checked-out tree. The default would be a
    Git context, which ignores the checkout.
  - `.dockerignore` applies as it does today.
  - `load: true` puts the image in the runner's Docker engine as
    `refs-ci-app:latest`.
  - `worker` and `web` are no longer built in CI. Nothing in CI ran them,
    and they share the same Dockerfile, so the build still fails on
    exactly the same errors.
- **Cache mode.** `cache-to: type=gha` keeps the default `mode=min`. The
  Dockerfile has a single stage, so every layer is in the final image, and
  `mode=max` would add nothing.
- **Tests** (`ci.yml:9`, unchanged). `docker compose run` builds only when
  the service's image is missing or `--build` is passed. With
  `COMPOSE_PROJECT_NAME=refs-ci`, compose looks for `refs-ci-app`
  (`docker-compose.yml:53-54` has `build: .` and no `image:`). It finds
  the loaded image, starts `db` (`docker-compose.yml:2-11`) and runs
  pytest in it. This is the same naming the local worktrees show
  (`refs-engine-45-app`, `refsdev-web`).
- **Scope.** `type=gha` uses one fixed scope key (`buildkit`). GitHub's
  cache rules make a run read its own branch's entries first, then the
  default branch's, and write to its own branch. That gives "per branch,
  falling back to `main`" without a branch key. A new branch starts warm
  from `main`'s last build.
- **Credentials.** `build-push-action` passes the Actions runtime token to
  BuildKit itself, so no secret or `permissions:` change is needed.

Pinning: major tags, as `actions/checkout@v4` already is. The latest
releases on 2026-10-09 are `docker/setup-buildx-action` v4.4.1 and
`docker/build-push-action` v7.4.0. Both run on Node 24, which needs Actions
runner 2.327.1 or newer; GitHub-hosted `ubuntu-latest` has it.
`actions/checkout` stays at `@v4` (v7 exists); bumping it is not this task.

What is cached: every layer up to `Dockerfile:17`. A warm run whose commit
changes only source under `app/` and `tests/` reuses `Dockerfile:2-16`
(apt, lock, pyproject, models, CA bundle). It rebuilds only
`COPY . .` (`:17`) and `useradd`/`USER`. A change to `requirements.lock`
rebuilds from `Dockerfile:8`, and a change to `pyproject.toml` from `:10`.
#42 ordered the layers this way for exactly this.

## Alternatives rejected

- **GHCR registry cache (`type=registry`).** No 10 GB cap, but it needs
  `packages: write`, a package to manage and prune, and a registry login.
  Rejected at the intent.
- **`actions/cache` over a local buildx cache directory.** This copies the
  whole cache in and out on every run and needs a manual move-and-replace
  so it doesn't grow without limit. `type=gha` stores layers one by one.
- **Keeping `docker compose build` with `cache_from`/`cache_to` in
  `docker-compose.yml`.** That puts CI-only settings in the dev file. It
  needs a buildx builder for compose anyway, and it builds three services.
- **`mode=max`.** It adds nothing for a single-stage Dockerfile.
- **A per-branch `scope=` key.** GitHub's cache isolation already gives
  per-branch reads with a `main` fallback. A branch key would break that
  fallback unless `cache-from` listed both keys.

## Risks

- **Cache size and eviction.** The image is 6.57 GB uncompressed (local
  `refs-*-app` images). Its compressed layers will be a few GB per
  branch, and GitHub caps a repo at 10 GB, evicting the least recently
  used entries. Two or three active branches can push out `main`'s
  entries, and the next run on `main` or a new branch is then cold
  (today's speed, not slower). Mitigation, if the after-runs show it: write
  the cache only on `main` (`cache-to` guarded by
  `github.ref == 'refs/heads/main'`). That would be a plan deviation and
  needs approval.
- **`load: true` cost.** Exporting a multi-GB image into the Docker engine
  takes time on every run, warm or cold. It may take back part of the
  saving. It is measured below.
- **Cold runs are slightly slower.** Exporting the cache adds time to a
  miss. This happens on the first run per branch only if `main` has no
  entry, and after every lock or Dockerfile change.
- **Image name coupling.** If someone adds `image:` to the `app` service, or
  renames it, compose no longer finds `refs-ci-app` and silently builds
  again with the plain driver: correct, but slow. The `env` comment names
  the coupling.
- **Fewer CI runs.** A branch with no PR gets no CI. A push to `main`
  outside a PR still runs.
- **Hosts:** GitHub-hosted runners only. The local dev stack, the ECS
  images and the `infra/` deploy are untouched.

## Verification

- **Before:** 276 s mean over the 22 most recent successful `ci` runs on
  2026-10-09 (217–423 s). Run 37896016908: build 3m51s, test 1m08s.
- **After:** on the PR branch, record three runs with `gh run view <id>
  --json jobs`:
  1. the first run, cold or warm from `main`;
  2. a second push with a source-only change, which must be warm;
  3. after merge, the first `push` run on `main`.

  Done when run 2's build step logs `CACHED` for the apt, lock, model and
  CA steps, and its total is clearly below 276 s. All the numbers go in the
  PR body.
- **Cache still catches a lock change:** a throwaway commit on the PR
  branch that edits the comment on `requirements.lock:2` must log the
  `pip install --require-hashes` step as run, not `CACHED`. Revert it
  before merge.
- **Tests use the built image:** the test step's log has no `Building`
  line, and pytest's pass count matches the latest run on `main`.
- **One run per PR push:** `gh run list --branch <branch>` shows one `ci`
  run per push, event `pull_request`.
