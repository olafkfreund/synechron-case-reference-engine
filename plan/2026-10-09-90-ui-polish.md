# Plan: Portal UI that is professional, modern and easy to use

## Approved decisions (self-contained)

- **Staged** in 5 stages (steps 1–5); the session model reloads the demo
  after each. **Word** is the one visible download. A **second Codex check**
  (read-only, on fresh demo screenshots) runs before the PR.
- The design review is `docs/reviews/2026-10-09-90-codex-ui-review.md`:
  read it before each step.
- **Rules everywhere:**
  - templates and `app/static/portal.css` only;
  - no new queries, routes, form `name`s or `value`s, and no access
    changes;
  - no JavaScript: `<details>`/`<summary>` and plain forms;
  - no new dependency or CDN;
  - every `name`d input, select or textarea gets a visible `<label for>`
    (or a wrapping `<label>`);
  - repeated buttons and checkboxes get row context in `aria-label`
    ("Save Demo: Bid library"), while their visible text stays;
  - inputs inside a closed `<details>` are never `required`.
- **Icons:** `app/templates/_icons.html`, `{% macro icon(name) %}`.
  Stroke-only inline SVG, 20px, `aria-hidden="true"`,
  `stroke="currentColor"`. The set: search, globe, inbox, users, database,
  shield, clock, file, check, alert.
- **Components** in `portal.css`:
  - `.page-head` (+`.page-head-actions`), `.stat-grid` / `.stat-tile`
    (big number, label, optional icon);
  - `.section-card` / `.card-head`, `.empty-state` (icon, a line, one
    next step);
  - `.field` / `.field-help`, `.action-row` (primary right, secondary
    left, wraps), `.detail-panel` (`<details>`, 44px `<summary>`,
    chevron, tinted body);
  - `.status-list` (`dl` key/value), `label.check` (a 44px hit area
    around a checkbox), and the existing `.avatar` reused for client
    initials.

  The existing tokens and badge colours are kept.
- **Header:** below 1500px, two intentional rows (brand and user, then
  tabs). The visible role is the highest one (admin > reviewer > user),
  with the full list in `title`.
- **Coder handoff:** 6 file-editing steps, so steps 1–6 go to the `coder`
  agent, one at a time. Step 7 is the session model's.


*Order change (the user's request, 2026-10-09):* step 4 (admin: Client
registry, then Sources, Model approvals, Audit) runs right after step 1,
before steps 2 and 3, because the user flagged the Client registry as
the page that most needs the rewrite. The content of each step is
unchanged.

   pytest tests/test_ui.py tests/test_auth.py -q`.
   Traps: no bind mount; the nav and logout stay as tested.
2. **Home and search:**
   - `landing.html`: a lead card "Find reference cases" (icon, line,
     button-styled link) with Research beside it, a "Needs review" card
     for reviewers, and the admin links as a 2×2 grid of small cards;
   - `search.html`:
     - the three filters labelled, in a `.row`;
     - each result a `.section-card`: a head with title, client label

       primary "Download Word", a `.detail-panel` "Other formats" holding

   → verify by `pytest tests/test_search.py tests/test_render.py

   Traps:

     the existing text and make it read well with CSS (or update the test

3. **Review:**

       list | length`, due soon = `due_soon | length`;

     - chips only for counts that aren't zero;
     - one calm line when nothing is due.
   - `review_detail.html`:
     - a `.page-head` with the case title (fallback "Case N") and status

     - a `.status-list` metadata card (document, source, external id,

       then "Fields", by looping twice over `rows` with a test;
     - each quote as a tinted panel;

   - `review_merge.html`: the same head and cards.

   → verify by `pytest tests/test_review.py tests/test_anonymise.py -q`.
   Traps:
   - keep `form="fN"` / `id="fN"`, the forms outside the tables, and
     `"<tr>\n<form" not in page`;
   - each row's form id must stay unique and stable across the two loops:
     compute it from the row's position in `rows`, not the loop index.
4. **Admin:**

   - `audit.html`: "Audit activity" with four summary tiles, a card per

   Traps:

   - no `required` inside closed panels.

*Step 4, clients (coder, two passes; the session model reloaded the demo
after each):* the first pass, a card per client, was too tall (3 clients
per screen), so the second makes it one list card with ~56px rows, compact
Edit and Delete… summaries, "+ Add client" in the page head, and "How
aliases work" as a link. All 10 clients fit at 1440px.
*Deviation (bug found by the user):* the browser kept the old cached
`portal.css` and showed the new markup unstyled. `base.html` now links
`/static/portal.css?v={{ css_version }}`, where `css_version` is the
stylesheet's content hash (a template global in `app/review.py`), so every
CSS change gets a new URL.


*Step 4 done (coder; checked by the session model):* sources, models and
audit are rewritten as the step says, and the edit panels are polished
(the open summary stays right-aligned; Access groups and Data class sit in
two columns at 900px and up). The full suite gives 514 passed. Note:
`test_hardening.py::test_audit_view_is_admin_only_paged_and_filtered`
counts every `<tr>` on the audit page, so it fails only when run after
tests that leave `source_*_changes` rows. That holds on main too, and it
passes in the full suite's order. It's a test weakness, so no change here.
