# Plan: MCP server, phase 4 (reviewer tools)

Worktree `../refs-engine-249p4`, branch `feat/249-mcp-phase4`, based on main
(phases 1–3, #259, #260 merged). One PR.

## Approved decisions (from the spec)

1. **Gate, checked on every reviewer tool call, in this order:**
   1. the phase 1 gate: a valid token, `refs.access`, an approved `azp`,
      and the user's groups
   2. the **reviewer** role
   3. `refs.review` in `scp`
   4. a live `model_approvals` row with `model = 'mcp-client:' || azp`,
      `data_class = 'confidential'` and `expires_at > now()`
   5. `load()`'s visibility and version checks: 404 when hidden, 409 when
      changed or closed

   - There is **no** `MCP_REVIEW_CLIENT_IDS` environment variable.
   - Each refusal gives the portal's text and is audited in `tool_calls`.
2. **`review.apply_edit(conn, user, cid, v, field, value=None,
   metric=None, start=None, end=None, quote=None, written=False,
   action="save") -> new_v`** is lifted from `POST /review/{cid}/edit`.
   The route becomes a wrapper with identical behaviour.
3. **Tools:**
   - `list_review_queue(page?)`: read-only, the `reviewable_cases` rows
     (id, title, status, action-note count, unsourced count, due)
   - `get_review_case(case_id)`: read-only, the allow-listed view plus `v`
   - `edit_case(case_id, v, field, …)`: writes, returns the new `v`, the
     field's state, and prose flags
4. **`get_review_case` allowlist.**
   - **Returned:** case id, status and basis; `fields[]` with label, path,
     values, quote and sourced, unsourced or written; `prose{}` with text,
     flags and by-reviewer; action notes only; completeness; the document
     title; `v`.
   - **Never returned:** `documents.text`, `external_id`, URLs, other
     cases, the uploader, public sources.
5. **Out of scope:** approve, reject, merge, architecture, diagrams and
   the registry. These stay in the portal.

## Deviations

- **Step 1.** `apply_edit` returns the new `v` with one extra select of
  `md5(data::text)` on the same connection. The portal route ignores it,
  so each portal edit costs one more query. `edit()` had no `friendly()`
  wrapper, so its error pages are unchanged.
- **Step 2.**
  - **How claims reach the tools.** They arrive through `_run(...,
    review=True)`, which already holds the verified token, so no new
    context plumbing was needed. `review=True` keeps the user's real
    roles; other tools still force `{"user"}`.
  - **Refusal text.** "this AI client is not approved to handle
    confidential data; an admin approves it under Model approvals".
  - **Tests.** The gate tests call `_run` directly, since no tool exists
    before step 3.

- **Step 3.**
  - **`edit_case` parameters.** It takes every edit-form parameter, with
    length caps, and `NAME.new` adds a list item.
  - **`get_review_case` visibility.** It uses the portal detail page's
    filter, so an approved case not yet in the queue is readable, and
    `edit_case` still needs it to be `OPEN`.
  - **Tests.** The tests insert a throwaway `jobs` row for the `uploads`
    foreign column.
- **Steps 4 and 5** (full suite 1456 passed):
  - **Smoke test.** It ran on the coder's own stack with no host ports:
    - the queue: 200, 4 rows
    - the case: 200
    - an edit: a new `v`
    - an edit with the stale `v`: `isError`, 409
  - **Demo groups.** The demo ACL groups mean a one-group mock token
    needs `ROLE_REVIEWER_GROUPS=delivery` for a local reviewer run.
- **Follow-ups** (full suite 1456 passed):
  - **Wording.** The MCP 409 text says "case changed; fetch it again with
    get_review_case and retry with the new v". The portal text is
    unchanged.
  - **Docs.** `docs/mcp.md` documents the local reviewer test: the
    one-group token, plus a `delivery` role override.
