# Plan: Reproducible image builds from a CPU-torch lock

## Approved decisions (self-contained)

- **`requirements.lock`** at the repo root, generated by `uv pip compile` in
  the pinned image `ghcr.io/astral-sh/uv:0.12.23-python3.12-trixie-slim`.
  - It pins every package, transitive ones included, with hashes, for
    Python 3.12 on `x86_64-manylinux_2_28`, with the `dev` extra.
  - `--torch-backend cpu` takes torch and torchvision from the PyTorch CPU
    index and everything else from PyPI.
  - uv is not installed in the image or on the workstation.
- **First lock:** today's working image's `pip freeze` is the constraints
  file. The lock contains exactly those 147 packages (docling 2.135.0,
  rapidocr 3.9.2, torch 2.14.1+cpu, torchvision 0.29.1+cpu, …).
- **Dockerfile:** pip installs the lock with `--require-hashes --no-deps
  --extra-index-url https://download.pytorch.org/whl/cpu`, then the project
  with `pip install --no-deps -e .` and `pip check`. The separate torch
  layer goes.
- **`pyproject.toml`:** names stay unversioned. The `rapidocr<3.10` cap from
  #70 is removed.
- **Updates by hand:** re-run the README command; add `--upgrade-package X`
  or `--upgrade` to move versions. No Dependabot.
- **Out of scope:** splitting dev from production images; pinning apt
  packages; ARM64 (documented as needing a re-lock).
- **Coder handoff:** 2 steps, 5 files. Steps 1 and 2 go to the `coder`
  agent. The session model runs step 3 (verification) and the review.

## Steps

1. **Lock and Dockerfile.**
   - `pyproject.toml` line 9: delete the `rapidocr<3.10` line.
   - Make the constraints from the current working image (built from main):
     `docker compose build app && docker run --rm
     synechron-case-referances-engine-app pip freeze --exclude-editable >
     <scratchpad>/constraints.txt`. Check that it has `rapidocr==3.9.2` and
     `torch==2.14.1+cpu`.
   - Generate `requirements.lock`, once only, with the constraints: copy
     `constraints.txt` into the repo root temporarily (the container only
     sees the mounted directory) and run

     ```sh
     docker run --rm -v "$PWD:/w" -w /w ghcr.io/astral-sh/uv:0.12.23-python3.12-trixie-slim \
       uv pip compile pyproject.toml --extra dev --torch-backend cpu --python-version 3.12 \
       --python-platform x86_64-manylinux_2_28 --generate-hashes \
       --custom-compile-command "see README: Dependency lock" \
       -c constraints.txt -o requirements.lock
     ```

     Then delete the temporary `constraints.txt`; it must not be committed.
     Fix the owner if the file comes out root-owned (`--user "$(id -u):$(id
     -g)"` on the `docker run`).
   - Check the lock against the freeze: the `name==version` lines (lowercased,
     `_` → `-`) are identical. Empty diff.
   - `Dockerfile` lines 7–10 become:

     ```dockerfile
     # pinned lock with hashes (see README: Dependency lock); CPU-only torch from its own index: Fargate has no GPU
     COPY pyproject.toml requirements.lock ./
     RUN pip install --require-hashes --no-deps -r requirements.lock --extra-index-url https://download.pytorch.org/whl/cpu
     RUN mkdir app && touch app/__init__.py && pip install --no-deps -e . && pip check
     ```

   → verify by `docker compose build --no-cache app && docker compose run
   --rm app pytest`: green. `pip list` in the image shows `torch 2.14.1+cpu`
   and no `nvidia-*` packages.

   Traps:
   - compose has no bind mount: build before running tests;
   - the lock must come from the edited `pyproject.toml` (without the cap),
     or the header and the resolve won't match;
   - don't let `constraints.txt` or a scratch file land in the repo
     (`git status` before committing);
   - keep the model download, RDS CA and apt lines unchanged.

   *Done (coder):* the lock vs freeze diff is empty (147 packages). The
   `--no-cache` build passes `pip check`. Full suite: 402 passed, the same
   count as main. The image has `torch 2.14.1+cpu` and no `nvidia-*`.
   *Deviation:* the `docker run` also needs `--user "$(id -u):$(id -g)" -e
   HOME=/tmp -e UV_CACHE_DIR=/tmp/uv`, so the lock isn't root-owned and uv
   can write its cache. The output is the same. The README command in step 2
   includes these flags.
2. **Docs.**
   - `README.md`: a new `## Dependency lock` section after `## Limits`
     (line 21). It says:
     - every image installs `requirements.lock` with hashes;
     - after editing `pyproject.toml`, re-run the command (the one above,
       without `-c constraints.txt`);
     - `--upgrade-package X` or `--upgrade` moves versions;
     - a dependency that isn't in the lock fails the build at `pip check`;
     - the lock is x86_64 only: for ARM64, re-lock with `--python-platform
       aarch64-manylinux_2_28`.
   - `infra/variables.tf` line 96: the description adds "ARM64 needs a
     re-lock (README: Dependency lock)".

   → verify by reading the README section and running its exact command
   (without constraints) on the committed lock: `requirements.lock` is
   unchanged (`git diff --exit-code`).
   Traps: the README command must be the same one step 1 used, minus `-c`.

   *Done (coder; finished by the session model):* the README section and the
   `cpu_architecture` note are in.
   *Deviation:* the step 1 lock carried `-c constraints.txt` in its
   `# via` comments, so the README command, which has no `-c`, could never
   reproduce it byte for byte. The committed lock is now the README
   command's own output: pins and hashes are identical to step 1 (the
   non-comment diff is empty), and only the comments changed. Running the
   README command again leaves the file unchanged.
3. **Verification (session model).**
   - Two `--no-cache` builds give an identical `pip freeze`.
   - Drift check: add `"tomli-w"` to `pyproject.toml`, build, and expect a
     failure at `pip check` (or a missing import). Then revert.

   → verify by those results, recorded here.

   *Done:* two `--no-cache` builds gave an identical `pip freeze` (149
   lines: the 147 locked packages, pip and the project). With `"tomli-w"`
   added to `pyproject.toml`, the build failed at `pip check`: "reference-engine
   0.1.0 requires tomli-w, which is not installed". Reverted.

*Review (fresh Opus): approved, no blockers.*
- *Deviation:* the Dockerfile copies `requirements.lock` and installs it
  before copying `pyproject.toml`. An edit to `pyproject.toml` alone then
  reuses the cached 147-package layer. CI always builds from scratch, so
  this only speeds up local rebuilds.
- Rollback note: reverting this PR also needs the `rapidocr<3.10` cap back
  (as `## Rollback` says), or the build breaks again.
- Not taken: pinning the `python:3.12-slim` base image by digest (out of
  scope).
