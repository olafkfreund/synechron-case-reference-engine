# Plan: Speed up CI with build caching

## Approved decisions (self-contained)

- **One file changes:** `.github/workflows/ci.yml`. The `Dockerfile`,
  `docker-compose.yml` and `.dockerignore` stay as they are.
- **Trigger:** `push` on `main` only, plus every `pull_request`. Branches
  without a PR get no CI. The job keeps the name `test`, which is the
  check #51 will require.
- **Build:** `docker/setup-buildx-action@v4` creates a `docker-container`
  builder. `docker/build-push-action@v7` builds `context: .`, never the
  default Git context, and loads the result (`load: true`) as
  `refs-ci-app:latest`. Latest releases on 2026-10-09: v4.4.1 and v7.4.0.
  Pin the majors, as `actions/checkout@v4` already is; checkout is not
  bumped.
- **Image name:** `COMPOSE_PROJECT_NAME: refs-ci` at job level. Compose then
  names the `app` service's image `refs-ci-app`, because `app` has
  `build: .` and no `image:` (`docker-compose.yml:53-54`).
  `docker compose run` builds only when the image is missing, so
  `docker compose run --rm app pytest` stays exactly as it is and uses the
  loaded image.
- **Not built:** `worker` and `web` (same Dockerfile, never run in CI).
- **Cache:** the GitHub Actions cache (`type=gha`), default `mode=min`,
  which is the same as `max` for this single-stage Dockerfile. There is no
  `scope=` key, so GitHub's rules let a PR run read `main`'s entries.
- **Decision at spec approval: only `main` writes the cache.** `cache-to`
  is `type=gha` on a push to `main`, and empty (no export) on a pull
  request. PR runs only read (`cache-from: type=gha`). This replaces the
  spec's per-branch writes and removes the risk that branch entries evict
  `main`'s under the 10 GB repo limit (the image is 6.57 GB uncompressed).
- **Out of scope:** the postgres pull in the test step; splitting images.
- **No secrets and no `permissions:` change.** `build-push-action` passes
  the Actions runtime token to BuildKit itself.
- **Before:** 276 s mean over the 22 most recent successful `ci` runs on
  2026-10-09 (217–423 s). Run 37896016908: build 3m51s, test 1m08s.
- **Coder handoff: none.** One step edits one file, which is under the
  threshold (3 editing steps or 3 files). The session model implements
  step 1 and runs steps 2–4. Review is by a fresh Opus agent.

## Steps

1. **`.github/workflows/ci.yml:1-9`: replace the whole file** with:

   ```yaml
   name: ci
   on:
     push:
       branches: [main]
     pull_request:
   jobs:
     test:
       runs-on: ubuntu-latest
       env:
         # fixes the compose image name for `app` to refs-ci-app (compose names it <project>-<service>)
         COMPOSE_PROJECT_NAME: refs-ci
       steps:
         - uses: actions/checkout@v4
         - uses: docker/setup-buildx-action@v4
         - uses: docker/build-push-action@v7
           with:
             context: .
             tags: refs-ci-app:latest
             load: true
             cache-from: type=gha
             # only main writes the cache, so PR branches can't evict it (10 GB repo limit)
             cache-to: ${{ github.event_name == 'push' && github.ref == 'refs/heads/main' && 'type=gha' || '' }}
         - run: docker compose run --rm app pytest
   ```

   → verify by
   `nix-shell -p actionlint --run "actionlint .github/workflows/ci.yml"`
   (no output), then `COMPOSE_PROJECT_NAME=refs-ci docker compose config
   --images | grep refs-ci-app`. That shows `refs-ci-app`, which is
   read-only and touches no running stack.

   Traps:
   - **The live dev stack.** Never run `docker compose up` or `down`. Don't
     run `docker compose build` or `run` locally under the default project
     name either. The workflow is tested on GitHub only.
   - **`context: .` is required.** Without it, the action builds from the
     Git ref and ignores the checkout.
   - **An empty `cache-to` must mean no export.** The `&& ||` expression
     yields `''` on pull requests. Confirm it in step 2's log: there is no
     `exporting cache` line.
   - **The image name is coupled to the `app` service.** Adding `image:` to
     `app`, or renaming it, makes compose build again with the plain
     driver. That is slow but still correct.
   - **Commit** as `ci: build with buildx and the GHA cache (plan #43
     step 1) (#43)`.

*Step 2 (session model), first PR run (run 37899658465, cold by design):*
8m53s in total, against a 276 s mean before. The build step took 6m47s
against 3m51s: of that, about 251 s is exporting layers (130 s) and
sending the tarball to docker (121 s), which `load: true` pays on every
run, warm or cold. pytest gave 410 passed, the same as main, with no
`Building` line and no `exporting cache`. *Review (fresh Opus):* no
blockers, but the warm run may not beat 276 s, because the load cost
recurs. Decision pending with the user before merge.


*Deviation (approved by the user as "rework"):* `load: true` sends the
6.6 GB image to Docker as a tarball on every run (about 250 s: exporting
130 s, sending 121 s). Instead:
- `docker/setup-docker-action@v5` turns on Docker's containerd image store
  (`daemon-config: {"features": {"containerd-snapshotter": true}}`);
- `docker/setup-buildx-action` uses the `docker` driver (`driver:
  docker`), so the build writes the image straight into Docker's store, with
  no tarball and no load. The containerd store lets the `docker` driver
  export the `gha` cache.
- Everything else is unchanged: `context: .`, the `refs-ci-app:latest`
  tag, `cache-from: type=gha`, `cache-to` only on push to main, and the
  test step.

Verify: the build log has no `sending tarball` and no `importing to
docker`, and the cold PR run is no slower than the 276 s baseline plus
the cache lookup. The warm run is still measured after merge (step 4).
