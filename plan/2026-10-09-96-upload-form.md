# Plan: Admin upload form in the portal

Approved decisions, carried over from the spec:

- One route, one validation path: `POST /admin/upload` stays the only upload
  entry point. It gains an optional `source_id` form field and a browser
  branch at its two exits (success and refusal). Type, size, magic bytes,
  `require("admin")` and the guard middleware are unchanged.
- A browser is a request whose `Accept` contains `text/html`. Browsers get a
  303 to `/admin/sources?notice=<code>`; API clients (curl, httpx, TestClient,
  which send `*/*`) keep today's status codes and JSON bodies.
- `source_id` absent → today's rule (lowest-id enabled upload source).
  `source_id` present → only that id, and only if it is an enabled `upload`
  source; otherwise 404 `"no such enabled upload source"`.
- Redirect URLs hold only the literal path `/admin/sources`, a fixed code and
  integers from the database. Nothing from the request goes in a URL.
- The Sources page shows a notice chosen from an allow-list (`NOTICES`) by the
  `notice` query param; unknown values show nothing. The source name comes
  from the database rows, autoescaped.
- The upload control is a `<details class="mini">` on each enabled upload-source
  row, next to "Crawl now", with the allowed types and size limit beside the
  picker. No JavaScript. Disabled upload sources and other kinds get none.
- The guard stays untouched: an oversize browser upload still gets the
  guard's JSON 413; the limit shown by the picker is the mitigation.
- Rejected (do not reintroduce): rendering sources.html from the upload route
  (import cycle), a session flash, echoing the file name, a second route, an
  HTML 413 from the guard, a source `<select>` in the page head.
