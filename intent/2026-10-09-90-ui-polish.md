# Intent: Portal UI that is professional, modern and easy to use

## Problem

#86 gave the portal the mockup's colours, type and components, but users
still see admin tooling more than a product. The user's example is the
Sources page:
- raw JSON config as the main table content;
- run counts as a seven-line dump;
- the access-group field squeezed to "sale" and the data-class select to
  "con";
- three long policy paragraphs above the table;
- Save and Crawl stacked.

A design review by Codex (read-only, with screenshots of every page on the
made-up demo data only; the full text is in
`docs/reviews/2026-10-09-90-codex-ui-review.md`) found the same pattern
across the portal:
- **No hierarchy:** home gives seven links equal weight; review list
  rows all look equally urgent; search results have five download buttons
  in two rows.
- **Help text and config bury the task:** Sources and Client registry
  open with policy paragraphs, and expose raw JSON and spreadsheet-like
  inputs.
- **Empty states look broken:** Model approvals shows only a table
  header, and Audit shows four separate "None" lines.
- **Form usability:**
  - inputs named only by placeholders or `aria-label` (search filters,
    source, client and model fields, the audit filter);
  - 18px checkboxes;
  - repeated "Save" / "Delete" / "Crawl now" with no row context;
  - tables without `<thead>`;
  - the header wraps at 1440px for admins.
- **Review detail:** the title is "Case 10" instead of the case name;
  metadata is crammed into one sentence; what approving does is only in a
  long button label.

## Proposed outcome

The portal reads as one product with a clear first action on every page:
- **Every page** opens with a consistent page head: title, one-line
  intro, status, primary action. Long guidance moves into `<details>`
  ("How aliases work", "Data classes", "Configuration and run details").
- **Home:** "Find reference cases" is the lead card with Research beside
  it, the review queue is a "Needs review" area, and admin links form a
  compact grid. Each card has a small inline-SVG icon.
- **Search:** visible labels on the filters; result cards lead with the
  title, client label, basis chip and "Why it fits"; one visible download
  action, with the five formats inside a "Download formats" disclosure; a
  real empty state.
- **Review list:** stat tiles (awaiting review, needs attention, due
  soon) from data the page already has; rows with a clear "Review case"
  action and chips only for counts that aren't zero.
- **Review detail:** the case title as heading, a metadata card,
  status chips, fields needing attention first, tinted source-quote
  panels, and a final action card that says unsourced fields are emptied
  on approval.
- **Sources, Client registry:** one summary row or card per item (name,
  kind, enabled/data-class chips, last run, key counts, initials avatar
  for clients); config JSON, all counts and edit fields in an "Edit /
  details" disclosure with full-width labelled inputs; Delete behind a
  disclosure.
- **Model approvals, Audit:** intentional empty states, a read-only
  "Data class: Confidential" line, labelled fields, "Audit activity" with
  section summaries and chips instead of yes/no.
- **Research:** a narrower task card, the "Ask → Preview query → Send"
  steps, the exact outgoing query in a prominent panel, and claims as
  compact source cards.
- **Header:** an intentional layout at 1440px, so it doesn't wrap for
  admins.
- **Shared components** in `portal.css`: `.page-head`, `.stat-grid` /
  `.stat-tile`, `.section-card`, `.empty-state`, `.field` / `.field-help`,
  `.action-row`, `.detail-panel`, `.status-list`, plus 44px hit areas for
  checkboxes and disclosures.
- Before and after screenshots of every page (demo data) go in the PR.

## Affected users and systems

- Everyone who uses the portal.
- `app/templates/*.html` and `app/static/portal.css`; possibly small
  display-only values passed from routes (for example, counts the
  template can compute itself). Not routes, queries, access, form
  `name`s or `value`s, the generated documents, or infra.

## Constraints

- **No JavaScript**, as today: `<details>`, CSS `:has()` and plain forms
  only.
- **No behaviour change:** same routes, form names and values, button
  text where tests rely on it, and access. All tests pass.
- **Accessible:** AA contrast, 44px targets, visible focus, real
  `<label for>`, and row context in accessible names.
- **No new dependency or CDN.** Icons are inline SVG.
- **Code is written by the `coder` agent** under the approved plan (org
  policy). Codex reviews: it did the design review, and it can check the
  implemented pages against its review before the PR.
- **Codex only ever sees** the repo and the made-up demo, never the
  `refsdev` stack or anything from the presale folder (data policy: it's a
  third-party model).

## Open questions

1. **Scope:** all pages in one issue, delivered in stages (shared
   components and the header first, then home and search, then review,
   then admin, then research), with the demo reloaded after each stage as
   for #86? I lean towards **yes, staged**.
2. **One visible download button:** which format is the default, Word or
   PDF? I lean towards **Word**: bid teams edit it; PDF and the rest are in
   the disclosure.
3. **Codex in the loop:** after implementation, run Codex once more,
   read-only, on new screenshots, as a second design check next to the
   Opus code review? I lean towards **yes**.
