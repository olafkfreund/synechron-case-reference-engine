# Intent: Uploaded documents are titled with the stored key, not the file name

## Problem

When a file is uploaded from the Sources page, the review queue and the
review page show a random prefix in front of its name, for example
`627f8e316ebe47598baa74ec5160c3fe-fictional-case.pdf`. The reviewer cannot
easily tell which file a case came from.

How it happens:

- `app/main.py:243-244` stores the upload at
  `{prefix}{uuid4().hex}-{safe_name(filename)}`. The random part stops two
  uploads with the same name from overwriting each other.
- `app/crawl.py` (`crawl_s3`) ingests every object with
  `title = key.rsplit("/", 1)[-1]`, which is the last part of the key.
- `app/ingest.py:104-110` stores that title in `documents.title`. The
  review list and review page show it (`app/review.py:119-143`).

S3 sources that people fill by hand are not affected. Their keys are the
real file names, so the title is already right.

## Proposed outcome

- A document uploaded through `/admin/upload` shows the uploaded file's
  name as its title, for example `fictional-case.pdf`. This holds for the
  Sources page form and for API callers.
- Titles of hand-filled S3 sources, SharePoint and Confluence documents do
  not change.
- Two uploads with the same name still get two separate S3 objects and two
  documents.

## Affected users and systems

- Admins who upload, and reviewers who read the queue.
- `app/main.py` (the upload route). Depending on the option, also
  `app/crawl.py` (`crawl_s3`).
- Tests: `tests/test_auth.py` (upload) and `tests/test_ingest.py`
  (crawl).
- No schema change. `external_id` stays the full S3 key, because it is the
  document's identity (`unique (source_id, external_id)`).

## Constraints

- The title is passed to `to_markdown(data, title)` (`app/ingest.py:95`),
  which reads the file type from its extension. The title must keep the
  extension that upload validated.
- The upload file name comes from the user. It must stay sanitised:
  - no path parts;
  - no control characters;
  - limited length.

  Templates already escape it on display.
- The random part of the key stays. Without it, a second upload with the
  same name would overwrite the first.
- Only made-up documents in tests and in the demo.

## Open questions

1. **How does the crawler learn the real name?**
   - **A. Key layout:** store uploads at `{prefix}{uuid}/{safe_name}`, so the
     last part of the key is the file name. This is a one-line change in
     `app/main.py`, with no crawler change. The title is the sanitised name,
     so `My Case!.docx` shows as `My_Case_.docx`.
   - **B. Object metadata:** keep the key. Store the original name as S3
     user metadata, percent-encoded because S3 metadata must be ASCII. In
     `crawl_s3`, use it when present and fall back to the last part of the
     key. `get_object` already returns the metadata, so there's no extra
     call. The title is the real name, cleaned of control characters and
     path parts.
   - **C. Strip the prefix:** in `crawl_s3`, strip a leading
     `<32 hex>-` from the last part of the key. This needs no change to
     upload, but it would also rename a hand-filled file that happens to
     start that way.

   **Recommendation: A.** It is the smallest change: one line, no crawler
   logic, and nothing for other S3 sources to trip over. The sanitised name
   is readable enough for a reviewer. Choose B only if exact original names
   (spaces, punctuation) matter.
2. **Fix documents already ingested?** The crawler's unchanged-checksum
   path (`app/ingest.py:~80-87`) does not update the title. So with A or B,
   an earlier upload keeps its old title until it is uploaded again.
   **Recommendation: no backfill.** Production is not deployed yet. The
   demo holds one such document, and `scripts/demo.sh reset` clears it.

## Approved answers

1. A: uploads are stored at {prefix}{uuid}/{safe_name}; no crawler change.
2. No backfill of documents already ingested.
