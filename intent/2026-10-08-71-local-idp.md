# Intent: Log in locally with test users

## Problem

The portal signs people in only through OIDC (`app/main.py` lines 140–186).
Without `OIDC_METADATA_URL`, `OIDC_CLIENT_ID` and `OIDC_CLIENT_SECRET`,
`/login` returns 503, and every page except login needs a session. Compose
runs no identity provider, so nobody can use the UI locally: not to try the
review, search, sources, research and admin pages, and not to check who sees
what.

Access is driven by groups from the ID token (the `groups` claim):

- **Roles:** `ROLE_USER_GROUPS`, `ROLE_REVIEWER_GROUPS` and
  `ROLE_ADMIN_GROUPS` map groups to user, reviewer and admin (admin implies
  reviewer implies user).
- **Documents:** each source's `acl_groups` decides which documents a user
  sees.

Testing that properly needs several users with different groups and a quick
way to switch between them. A real company identity provider makes that
slow: real accounts, real group changes, an app registration.

## Proposed outcome

- One command (`docker compose --profile dev up`, or similar) starts the
  portal with a local identity provider.
- Test users can log in at http://localhost:8000, at least:
  - an admin;
  - a reviewer;
  - a user in one document group;
  - a user with no role (gets 403 on pages that need a role).
- Their groups reach the app exactly as a real provider's would, through the
  real login code path, so role and document access behave as in
  production.
- The README says how to start it and lists the test users.

## Affected users and systems

- `docker-compose.yml`, possibly a small config file for the provider, the
  README.
- Developers and testers on a workstation.
- Not the AWS images, infra or production login.

## Constraints

- Dev only: nothing of it in the Dockerfile, `infra/` or production
  settings. Test passwords are fake and committed on purpose; this must be
  obvious.
- No test-only login shortcut in the app (no "dev login" route that skips
  OIDC). The real `/login` and `/auth` code must be what gets tested.
- The provider runs in a container from a public image, pinned by version.
- The existing `docker compose run --rm app pytest` and CI stay as they are.

## Open questions

1. **Which provider.** Options:
   - Keycloak: complete, but heavy and slow to start.
   - Dex: light, but its built-in password users have no groups.
   - A mock OIDC server (for example navikt `mock-oauth2-server`): light, and
     lets the tester type any user and groups at login.

   The spec picks one. I lean towards the mock server, because switching
   groups per login is exactly what access testing needs.
2. **The browser and the app see the provider at different addresses**
   (`localhost:<port>` vs the compose service name). The token issuer must
   match both. The spec has to solve this without changing app code if
   possible.
