# Intent: Speed up CI with build caching

## Problem

Every CI run builds the whole image from nothing. The runner is a fresh
`ubuntu-latest` VM (`.github/workflows/ci.yml:5`) with no Docker cache, so
`docker compose build` (`ci.yml:8`) re-runs every Dockerfile layer each time:

- the apt install of LibreOffice and the GL libraries (`Dockerfile:2-4`);
- the install of the hashed lock, 3,606 lines including CPU torch
  (`Dockerfile:8-9`, `requirements.lock`);
- the Docling model download from Hugging Face (`Dockerfile:13`);
- the RDS CA bundle download (`Dockerfile:15`).

The Dockerfile is already ordered for caching: since #42 the lock is
copied before `pyproject.toml` (`Dockerfile:8-10`), and the source comes last
(`Dockerfile:17`). On CI none of that helps, because no cache survives
between runs.

Measured with `gh run list` / `gh run view` on 2026-10-09: the 22 most
recent successful `ci` runs took 276 s on average (about 4.5 minutes),
between 217 s and 423 s. In run 37896016908 the build step took 3 min 51 s
and `docker compose run --rm app pytest` (`ci.yml:9`) took 1 min 8 s, which
includes pulling `postgres:16` and waiting for its healthcheck
(`docker-compose.yml:2-11`).

Every push to a branch with an open PR also runs CI twice, once for `push`
and once for `pull_request` (`ci.yml:2`; e.g. runs 37896016908 and
37896020482 on `feat/40-review-list-edit`, three seconds apart). That
doubles the runner time but not the wait.

The cost is the wait on every push, and on every review-fix round in the
intent → spec → plan workflow. It also matters for #51, which will make CI a
required check on `main`.

## Proposed outcome

- A CI run whose commit leaves `Dockerfile` and `requirements.lock`
  unchanged reuses the dependency and model layers instead of rebuilding
  them. Its log shows those steps as cached.
- A change to `requirements.lock` or the Dockerfile still rebuilds from the
  first changed layer, so CI still catches a broken lock (the failure that
  #42 was about).
- Run time is recorded before (276 s mean, above) and after, in the PR, as
  issue #43 asks.
- The tests run in the same image the build produces, as today.

## Affected users and systems

- `.github/workflows/ci.yml`; possibly `Dockerfile` and `docker-compose.yml`
  if the spec needs it.
- GitHub Actions cache storage for the repo (the image is large: torch,
  LibreOffice, Docling models).
- Everyone who pushes a branch, and the CI check that #51 will require.
- Not affected: the local dev stack and the ECS images. `docker compose`
  locally already keeps its own layer cache.

## Constraints

- Must not change what is installed: same lock, same `--require-hashes`
  install, same CPU torch (`Dockerfile:9`).
- Must not weaken the build check: a cache must never hide a Dockerfile or
  lock change.
- Docling models are still fetched at build time; no runtime egress
  (`Dockerfile:6`, `Dockerfile:12-13`).
- No new secrets or registry credentials unless the spec shows they are
  needed; the repo has none for CI today.
- Must keep working on forks' PRs as far as GitHub allows (cache writes are
  restricted there).
- The local dev workflow (`docker compose build`, `docker compose run --rm
  app pytest`) stays unchanged.

## Open questions

1. **Where the cache lives.** (a) The GitHub Actions cache (`type=gha` via
   buildx), with a 10 GB per-repo limit; (b) a registry cache in GHCR
   (`type=registry`), with no size cap but packages to manage; (c)
   `actions/cache` over a local buildx cache directory. Lean: (a), no new
   credentials or packages; the spec checks the cached size fits under the
   limit.
2. **compose or plain buildx.** `docker compose build` builds `app`, `worker`
   and `web` from the same `build: .` (`docker-compose.yml:53-54, 60-61,
   83-84`). Keep compose and add `cache_from`/`cache_to` (in the file or a
   CI-only override), or build once with `docker/build-push-action` and tag
   it for compose. Lean: build once with buildx and load it as the image
   compose uses for `app`; it is the one CI runs, and it avoids putting
   CI-only cache settings in the dev compose file.
3. **Duplicate push + pull_request runs** (`ci.yml:2`). Restrict `push` to
   `main` so a PR branch runs once? Lean: yes, but it changes when branches
   without a PR get CI, so the approver decides; it could also be its own
   issue.
4. **Cache scope.** Per branch with fallback to `main`, or `main` only?
   Lean: GitHub's default (branch, then default branch), so the first run
   on a new branch starts warm from `main`.
5. **The test step** (68 s, part of it pulling `postgres:16`). Lean: out
   of scope; it is a small image and not what the issue names.
