# Intent: Portal UI matches the approved mockup

## Problem

Users were shown the [portal mockup](https://claude.ai/artifact/51aJ7CQx77Wynaukd9N2Fj)
(README, "Links"). The real portal looks nothing like it. Every page is
unstyled HTML: one 8-line `<style>` block in `app/templates/base.html`,
system fonts, browser-default links and buttons, a bulleted list of links
on the home page (`landing.html`), and bare tables everywhere else. In the
first demo to users (2026-10-09) this was the main reaction: the portal
looks unfinished, which undermines trust in what it shows.

The mockup's look, for reference:
- **Header:** dark navy bar (`#1B2430`) with "Reference Engine · bids &
  presales", tab navigation, and the user's initials and role on the
  right.
- **Ground and accent:** warm off-white page (`#F6F5F1`), teal accent
  (`#0B6A6A`) for primary buttons, links and focus rings.
- **Type:** IBM Plex Sans for text, IBM Plex Mono for metadata (source,
  ids, tech tags, counts).
- **Components:**
  - white cards (1 px `#DAD7CF` border, 10 px radius);
  - pill badges (approved green, warning amber, neutral grey, anonymised);
  - 44 px buttons (primary teal, secondary outline, dark download);
  - amber notes;
  - tables with a tinted header.
- **Layouts:**
  - search: a bid box, then result cards with outcomes, tech tags, the
    tailored wording box, a source quote and the download buttons;
  - review: a field / value / source sentence / check table;
  - sources, client registry and audit: wide tables in a scrolling box.

## Proposed outcome

- Every page uses the mockup's header, colours, type and components.
- Search, review, research and the admin pages follow the mockup's
  layouts, showing the data the portal has today. No invented fields: the
  mockup's columns that the app doesn't have yet are left out, not faked.
- The home page becomes the user's start point: the tabs they may use (by
  role), not a bullet list.
- The look is the same for every role. A user sees only the tabs and
  buttons their role allows, as today.
- The mockup's "illustrative sample data" banner is not copied into the
  real portal.

## Affected users and systems

- Everyone who uses the portal.
- `app/templates/*.html`: all 12 templates, mostly markup and classes.
  One shared stylesheet, and font files.
- Not: routes, queries, access checks, the generated Word, PowerPoint and
  PDF documents (those follow marketing's templates, #15), infra.

## Constraints

- **No JavaScript**, as today. The mockup's tabs become plain links, and
  its buttons stay real `<form>` posts.
- **No change to behaviour:** same routes, form fields and access. All
  existing tests pass unchanged, except tests that match on exact
  markup.
- **Accessible:** text contrast 4.5:1, visible keyboard focus, 44 px
  targets, real `<button>` and `<label>` elements, and the layout works at
  phone width.
- **Autoescape stays on**, with no `|safe` on user data.
- **No new Python dependency.**

## Open questions

1. **Fonts:** load IBM Plex from Google Fonts (as the mockup does), or
   ship the font files in the repo and serve them from the app?
   - Google Fonts tells Google which portal page a user opened, and fails
     where the network blocks it.
   - IBM Plex is open-licensed (OFL), so self-hosting is allowed.

   I lean towards **self-hosting** (four `.woff2` files, about 200 KB),
   with the system font as the fallback.
2. **Where the CSS lives:** keep it in `base.html`, or serve
   `app/static/portal.css`? I lean towards **a static file**, cached by the
   browser, with FastAPI's built-in `StaticFiles`, so no new dependency.
3. **Pages the mockup doesn't show** (model approvals, the merge preview,
   the research view): style them with the same components. I lean
   towards yes, the same components, without separate mockups.
