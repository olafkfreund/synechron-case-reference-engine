# Intent: Admin upload form in the portal

## Problem

`POST /admin/upload` (app/main.py:210-236) takes one multipart `file`, but
nothing in the portal posts to it. The Sources page (app/templates/sources.html,
reworked in #90) has forms to add, edit and crawl a source, and none to upload.
So an admin can upload only with curl, and the README demo step "upload a
document to 'Demo: Bid library'" (README.md:108) has no button to click. Found
while writing the user guide (#38).

The endpoint is also built for an API client, not a browser:
- on success it returns JSON `{"job_id": …}` with 202 (app/main.py:236), where
  the other Sources forms redirect back with 303 (app/sources.py:87, 118, 129);
- every refusal is an `HTTPException` (app/main.py:216, 219, 221, 226), which a
  browser shows as a raw JSON body; only 401 has an HTML handler
  (app/main.py:133-138);
- it always uses the lowest-id enabled `upload` source (app/main.py:223-224),
  so with two upload sources the admin cannot choose and is not told which
  one got the file.

## Proposed outcome

- An admin uploads a .docx, .pptx or .pdf from the Sources page with a plain
  form and a file picker. No curl.
- The same file is accepted or refused exactly as today: type by extension,
  size cap `UPLOAD_MAX_BYTES` (app/main.py:82-83), magic bytes
  (app/main.py:22), at least one enabled upload source.
- After the upload the admin is back on a portal page that says the file was
  queued, and to which source; a refusal shows the reason as a page, not JSON.
- curl clients keep working: same path, same 202 JSON and status codes, so
  tests/test_auth.py:57-149 pass unchanged.

## Affected users and systems

- Admins (role `admin`, `require("admin")`); no other role sees the form.
- app/main.py: `upload` route (210-236) and its response.
- app/templates/sources.html: the form.
- app/sources.py: `sources_page` (52-57) may need to pass the upload sources.
- The guard middleware (app/main.py:117-130): unchanged, but the form must pass
  its Origin check and its size check (126-129).
- tests/test_auth.py: new tests for the form path.
- README.md:68 and 108: the demo steps can name the button.

## Constraints

- No JavaScript: a plain `<form method="post" enctype="multipart/form-data">`.
- Same checks as the endpoint, in the same code: type, size, magic bytes, the
  admin role, the guard's Origin and Content-Length checks. No second
  validation path that can drift.
- The guard must not be loosened: a browser form post sends `Origin`, so it
  passes as is (app/main.py:122-124).
- Tests use made-up data only: the existing fake `DOCX`/`PDF` byte strings,
  invented file and source names. No real customer documents. The repo is
  public.

## Open questions

1. **Where the form lives.**
   a) In the Sources page head, beside "+ Add source", as a second
      `<details>` panel; b) per upload-source row, an "Upload" control next to
      "Crawl now"; c) a separate `/admin/upload` page.
   Lean: b) if Q2 picks "admin chooses", since the row already names the
   source; otherwise a).
2. **Which source, when there are several upload sources.**
   a) Keep the rule: lowest-id enabled one (app/main.py:223-224), and say its
      name on the result; b) the admin picks: an optional `source_id` field,
      checked to be an enabled `upload` source, falling back to the rule when
      absent so curl is unchanged.
   Lean: b). Upload sources can differ in data class and access groups, so a
   silent pick can give a file the wrong readers.
3. **What the admin sees after upload.**
   a) 303 back to `/admin/sources` with a one-line notice ("Queued <file> to
      <source>, job <id>"); b) a small result page with the same text and a
      link back; c) leave the JSON.
   Lean: a) for success, matching the other Sources forms. Tell the form post
   from curl by `Accept: text/html`, as the 401 handler does (app/main.py:136),
   so curl keeps 202 JSON.
4. **How refusals show.** Lean: for an HTML request, render the reason
   (wrong type, too large, content does not match, no upload source) on the
   Sources page; JSON for API clients as now. A 413 from the guard happens
   before the route and stays JSON; acceptable, or should the guard also
   answer HTML? Lean: leave the guard alone and state the size limit next to
   the file picker.
