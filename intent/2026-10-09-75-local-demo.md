# Intent: Local demo with persistent made-up data

## Problem

The user wants to show the portal, and the data it creates, to future
users, collect their feedback, and improve it. A local demo is enough,
but it must run on a workstation **without changing the host**: only
Docker and this repo. No `/etc/hosts` line, no installs, no config files
outside the repo.

Today (`docker-compose.yml` after #71):

- **Empty.** `docker compose up web worker` starts a portal with no
  sources, cases or registry clients. Before there's anything to show, a
  presenter has to create a source, upload documents and wait for
  extraction.
- **Not persistent.** `db` has no volume, so `docker compose down` wipes
  every case and review decision. The `s3` service (moto) keeps files in
  memory, so a restart loses the stored originals.
- **Needs a model.** Turning an upload into a case, search tailoring
  (`app/search.py:95`) and research claims (`app/research.py:335`) call a
  model. Locally that's the host's Ollama, with four `export`s from the
  README.
- **Thin cases.** The one hand-made demo case so far (case 2) came out of
  `qwen3:14b` with no title, and with outcomes named "metric". A demo built
  only from live local extraction may show the model's weak spots instead
  of the portal.

## Proposed outcome

- **One documented command** (for example `scripts/demo.sh up`) starts the
  stack and loads a demo data set the first time. Then the presenter opens
  http://localhost:8000.
- **The demo data is made up** and covers what users should see:
  - a handful of sources of different kinds and access groups;
  - about 10 to 15 cases across industries and regions: delivered cases
    and engagements (#52), approved and waiting for review, with sourced
    and unsourced fields;
  - registry clients, including a non-referenceable one, so
    anonymisation shows;
  - the stored original documents, so review and re-extraction work.
- **Every role has something to do.** `admin` sees sources, clients,
  models and the audit log; `reviewer` has a review queue; `sales` can
  search and generate outputs; `nobody` gets 403. The README test users
  are reused.
- **The data survives** `docker compose down` and up, and the same command
  can **reset** it to the original demo set on purpose.
- **With a model** (the host's Ollama, if it's already running, or
  Bedrock), uploads, search tailoring and research work live on top of
  the demo data. **Without a model**, the seeded data can still be browsed,
  reviewed and approved, and the README says what needs a model.
- A short **demo walkthrough** in the README: what to click, as which
  user, and what it shows.

## Affected users and systems

- Presenters and the users they demo to; developers who want realistic
  local data.
- `docker-compose.yml` (volumes, maybe a seed service), a new seed script
  and made-up demo documents under the repo, the README.
- Not the app code, the Dockerfile's production use, `infra/` or AWS.

## Constraints

- **No host changes:** Docker only. Ports stay `127.0.0.1:8000` and
  `127.0.0.1:8080`. Nothing written outside the repo and Docker's own
  volumes.
- **Made-up data only.** No content from the confidential presale
  documents, and no real client names. The fictional names must not
  collide with real Synechron clients; use obviously fictional ones (for
  example Contoso, Northwind, Fabrikam).
- Seeded cases go through the same schema (`ReferenceCase`) and source
  check (`check()`) as extracted ones, so the demo doesn't show data the
  real pipeline couldn't produce.
- CI is unchanged: `docker compose build` and `docker compose run --rm
  app pytest` don't load or need demo data.
- The mock login provider stays local only (#71).
- No new dependencies.

## Open questions

1. **Where the demo cases come from.**
   - (a) Pre-written case JSON, loaded straight into the database next to
     its document text: fast, no model, the same result every time.
   - (b) Real extraction of the made-up documents through the local
     model at first start: shows the real pipeline, but it's slow
     (minutes per document on CPU), needs a model, and the quality varies.

   I lean towards **(a) for the seed, with (b) shown live** by uploading
   one more made-up document during the demo, when a model is available.
2. **A model in the demo.**
   - (a) Use the host's Ollama if it's reachable, with the model settings
     in a repo file (`.env.demo`) instead of `export`s.
   - (b) An Ollama container in compose: no host dependency, but a
     multi-GB model download, and slow on CPU.
   - (c) No model.

   I lean towards **(a), optional**: the demo works without it, and
   live extraction lights up when it's there. On a machine without
   Ollama, (b) can come later.
3. **S3 persistence.** moto keeps files in memory.
   - Give it a volume, if moto's persistence works for S3.
   - Swap in another small S3-compatible server.
   - Re-upload the demo originals from the repo on every start.

   I lean towards whichever the spec shows works with the fewest moving
   parts; re-uploading from the repo is the fallback.
4. **Generated outputs** (Word, PowerPoint): do they work locally without
   the marketing templates (#15)? The spec checks. If they don't, the demo
   leaves outputs out and says so.
5. **Separate from development?** A `demo` compose profile or project name
   (`-p refsdemo`) keeps demo data apart from a developer's own local
   data. I lean towards a separate project name in the script.
