# Intent: An MCP server, so anyone at Synechron can use the reference engine from their AI agent

## Problem

The reference engine is only reachable through the portal. Bid teams
increasingly work inside AI agents (Claude Code, VS Code/Copilot, Cursor).
From there they can't do any of these:

- search references
- read a case
- preview or download a bid pack or case study
- run research and use the library
- upload a document for indexing
- work the review queue

They have to switch to the browser and copy text back by hand.

## Proposed outcome

A remote MCP server at `https://<host>/mcp`, inside the existing app, that
every Synechron user connects to from their AI client.

- **Each user signs in as themselves** through Entra ID. They get exactly the
  portal's permissions: roles, document ACLs, anonymisation, review gates and
  audit.
- **Tools:**
  - search and read references
  - list the latest references
  - preview and generate documents, returned as a short-lived download link
  - research, library and briefs
  - upload a document for indexing, open to every user; it goes to review
    and becomes visible to all staff only after approval
  - for reviewers, from approved AI clients only: read and edit draft cases
- **Approval stays in the portal.**
- **Delivered in phases**, each its own PR and its own spec and plan:
  - 0: feasibility spike on a dev tenant
  - 1: identity and read-only tools
  - 2: outputs and research
  - 3: uploads for everyone
  - 4: reviewer tools
  - 5: Claude Desktop/claude.ai, after a security sign-off on public ingress
- **One install guide** (`docs/mcp.md`) for Claude Code, VS Code and Cursor,
  plus local development against the mock IdP.

The full approved design, including the tool catalogue, data rules,
verification and the findings of both reviews, is in `docs/mcp-design.md`.
It was approved in plan mode on 2026-10-13, after research and an
adversarial review by Fable and Codex.

## Affected users and systems

- **Users:** every Synechron user, as users of the AI tools; reviewers; and
  admins, who handle the Entra app registration.
- **App:** `app/main.py` (auth and guard), service-function lifts in
  render, review, research, library and ingest, a new `app/mcp_server.py`,
  and new tables (`user_keys`, `tool_calls`, `uploads`).
- **Identity:** the user key moves from the ID token's `sub` to Entra `oid`,
  with a one-off backfill.
- **Infra:** none until phase 5. The ALB stays internal.

## Constraints

- **Data that may leave:** only approved, anonymised, ACL-visible content
  goes into a user's AI tool. Raw document text never leaves. The stored
  source URLs never leave either; tools give portal `/go` links instead.
- **Credentials:** no shared service token and no token passthrough. Tokens
  are validated for issuer, audience, scope and expiry, and the client id is
  the signed `azp` claim.
- **No bypass:** no tool approves, rejects, merges or administers, and no
  case is created without a source document.
- **Audit:** every tool call is recorded without arguments or content.
- **Spec support:** MCP 2026-07-28 and 2025-06-18, through the official
  Python SDK, pinned.

## Open questions

- **Phase 0 needs a dev Entra tenant** and permission to create an app
  registration. Who provides it, and when? Without one, phases 1–4 run
  against the mock IdP only, and the real-client login steps stay
  unverified.
- **Which client ids to pre-authorise** for the reviewer scope. This can wait
  until phase 4.
