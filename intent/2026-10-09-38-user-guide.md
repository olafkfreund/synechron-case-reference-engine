# Intent: User guide for bid team, reviewers and admins

## Problem

The portal has three roles (user, reviewer, admin, from `roles_for()` in
`app/main.py`) and no guide for any of them. The README covers developers
only: limits, the dependency lock, test logins, the demo. So:

- **Bid team (user role)** doesn't know how search ranks cases, which
  download format to pick, what research sends out (Ask → Preview → Send),
  or why an output with no case asks for an acknowledgement
  (`app/render.py:356`).
- **Reviewers** can't tell from the page alone what "sourced" and
  "unsourced" mean, that approval drops unsourced fields, or when a case
  comes back for re-review.
- **Admins** have to read code to set up sources (config, access groups,
  crawl), the client registry, model approvals and the audit log.

Questions go to the developers instead.

## Proposed outcome

- **Readers:** bid team members, reviewers and admins. Not developers.
- **Tasks covered** (the issue's "Done when"):
  - Bid team: log in, search, read a result, download (Word and other
    formats), research with preview and send, and the acknowledgement for
    an output with no case.
  - Reviewers: the review list, sourced vs. unsourced fields and quotes,
    edit, add and remove list items, approve, reject, merge and unmerge,
    re-review.
  - Admins: sources (add, edit, access groups, crawl, upload, skip
    counts), client registry, model approvals, audit.
- **Version:** describes the UI from PR #94 (`feat/90-ui-polish`), so the
  labels and buttons match what users see after it merges.
- **Format and place:** short task-based Markdown pages, one section per
  task: what it's for, the steps, what you see. Place and split are open
  questions below.

## Affected users and systems

- Bid team, reviewers, admins; whoever onboards them.
- New docs only. No change to `app/`, routes, templates, tests or infra.
- README gets one link to the guide.

## Constraints

- **The repo is public.** Made-up examples only: no client names, no real
  case content, people, hosts or URLs.
- Screenshots only from the made-up demo (`scripts/demo.sh`, project
  `refsdemo`), never from refsdev or a real deployment.
- Match the #94 UI wording exactly; if #94 changes before merge, the guide
  follows it.
- Describe what each role can do, not how access checks work inside.

## Open questions

1. **Place:** `docs/user-guide/` in the repo, or a help page served by the
   portal? Lean: `docs/` in the repo. No code, reviewed like any change;
   a portal link can come later.
2. **Screenshots:** none, a few, or one per task? Lean: a few, one per main
   page at desktop width, from the demo. Each one goes stale when the UI
   changes, so no more than needed.
3. **One guide or one per role?** Lean: one per role (`bid-team.md`,
   `reviewers.md`, `admins.md`) plus a short index. Each reader opens only
   their page; admins and reviewers also have the user role, so the index
   says that.
4. **Wait for #94 to merge first?** Lean: write it now against the branch,
   merge after #94.
